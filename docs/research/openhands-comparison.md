# Rocky vs. OpenHands

_Research date: 2026-09-16. OpenHands facts are based only on official documentation and upstream source pinned below._

## Bottom line

OpenHands can produce a **similar end result** to Rocky today: receive an issue or webhook, run a coding agent in a workspace, open a pull request, review and test it, react to follow-up events, and iterate until it is ready. Its SDK, sandbox choices, agent customization, and observability are broader than Rocky's.

It is **not an off-the-shelf replacement for Rocky's workflow semantics**. Rocky is an opinionated, durable workflow product: a typed visual graph, journaled steps that replay after restart, explicit parking/checkpoints, revision-aware review and merge gates, multi-repository workspaces, and a run UI organized around those concepts. OpenHands is a general agent runtime plus a conversation UI, a beta automation scheduler, and installable skills/plugins. Matching Rocky closely means building a coordinator on top of OpenHands; most of the work is orchestration, persistence guarantees, SCM policy, and UX—not the coding agent itself.

The practical recommendation is therefore:

- Use OpenHands alone when “issue/webhook → agent → PR → review/QA/CI iteration” is sufficient and conversation-centric, partly agent-driven control is acceptable.
- Keep Rocky's coordinator and add OpenHands Agent Server as another execution backend when Rocky's replay, checkpoints, evidence, Linear experience, multi-repo coordination, or merge guarantees are requirements.
- Rebuild Rocky's coordinator as an OpenHands automation/script service only if consolidating on the OpenHands stack is worth substantial custom product work.

## What the new conversation-continuation support changes

The current Automation Service is closer to Rocky than older comparisons suggest. An `EventTrigger` can route matching events to `continue_conversation`; derive a stable external subject such as a PR or Slack thread; turn a payload field into the next user message; wake the agent immediately or buffer the message; coalesce events that arrive while the first run is still queued; and retain the sandbox because the conversation outlives the run. The automation-scoped KV API also supplies encrypted, persistent cross-run state and optimistic concurrency operations.

That is enough to keep PR comments, review feedback, or Linear-like webhook updates attached to one agent conversation. It is not equivalent to Rocky's journal: neither the event stream nor KV store defines a graph program counter, replay-safe side-effect protocol, completed-step cache, bounded review-loop policy, or approval bound to a particular PR revision. Those semantics can be encoded in a custom script/service using OpenHands primitives, but OpenHands does not supply them as a product contract.

## How to implement it with OpenHands

### 1. Fastest similar system

Run Agent Canvas with Agent Server and Automation Server. Add a signed Linear webhook automation (or poll Linear), key continuation by issue identifier, and install or adapt the GitHub issue-to-PR, PR-review, QA, and `/iterate` extensions. Use OpenHands natively or an ACP profile for Claude Code/Codex. This gets the common coding outcome quickly, but the automation is still one conversation whose script/agent decides much of the loop.

### 2. Near parity with Rocky

Implement a custom automation script bundle or adjacent coordinator with an explicit state machine:

1. Persist workflow/run/step state in PostgreSQL; use automation KV only for small automation-scoped coordination data.
2. Treat OpenHands Agent Server REST/WebSocket as the execution boundary. Create separate conversations for clarify, implement, review/fix, QA and recap roles, with structured `FinishTool` schemas.
3. Implement deterministic Linear/SCM/CI adapters outside the model. Record effect keys so retries do not duplicate comments, branches, PRs or merges.
4. Store evidence and tie every review, CI result and approval to the exact repository/PR/head SHA. Re-open the loop when the head changes.
5. Add the multi-repository workspace and multi-PR merge coordinator Rocky already owns.
6. Present the workflow through a separate UI or a Canvas App backed by the coordinator; the beta App API alone cannot replace the existing conversation visualizer or subscribe directly to Agent Server WebSockets.

At that point OpenHands supplies excellent agents, workspaces, sandboxing, conversation persistence and telemetry, while the custom layer supplies the feature that makes Rocky distinctive. Architecturally, that also makes the lowest-risk migration path clear: retain Rocky's TypeScript workflow engine and integrate the Python OpenHands stack through Agent Server's REST/WebSocket API rather than porting Rocky into agent prompts.

## Decision

**Yes, similar is possible. Exact parity is possible only with custom orchestration.** OpenHands is the better execution substrate if isolation, remote backends, native agent extensibility, ACP compatibility, and OpenTelemetry matter most. Rocky is the better finished workflow layer when deterministic, inspectable, restart-safe software-delivery policy matters most. The two are complementary enough that adding OpenHands as a Rocky harness/runtime is likely cheaper and safer than replacing Rocky with prompt-driven automations.
