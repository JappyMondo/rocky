# Durable coordinator contract slice

Taskbot #53 implements local coordinator state and dispatch contracts. It does **not** implement or qualify a live Codex harness, Attraccess coding check selection, independent target acceptance, GitHub publication, or a successful coding delivery. The existing accepted environment qualification is historical evidence and is unchanged.

## Ownership and persistence

`Store.admitCoordinator` creates a versioned scope/snapshot and repository/issue ownership in the same SQLite database as foundation runs, append-only events, effects and commands. A repository/issue has one current run. An explicit rerun names the previous terminal, quiescent run and a new rerun identity; old owners cannot revive it after transfer. Workspace identity stays attached to its run.

`ingestCoordinator` deduplicates by `(source, eventId)`. An identical retry is harmless, but changed payload or run identity under that key is rejected. IDs must therefore include the upstream source namespace. Sources are trusted host entrypoints, **not authentication**. An agent result can report changed/no-code/failed/interrupted execution; it cannot submit authoritative check, review, CI or approval verdicts through this entrypoint.

`applyCoordinator(lease, expectedRevision, source, eventId)` starts `BEGIN IMMEDIATE`, validates fencing/versions/revision, reduces the persisted event, and atomically writes the consumed inbox marker, new snapshot, monotonically reserved budgets, global slot, existing effect outbox intent and append-only transition event. An exception rolls everything back. A retry of a consumed event returns current state without spending again. The transaction only runs synchronous local code.

Coordinator snapshots cannot be changed with the older generic `transition` or `revise` APIs. Foundation cancellation still immediately revokes dispatch; the next coordinator event incorporates it. The coordinator snapshot schema is 3, separate from SQLite storage schema 5 and pinned workflow/adapter/prompt/runner/build versions. Unknown snapshot or storage versions fail closed. Version changes do not silently upgrade an active run.

## Schema compatibility

Opening an owned storage-schema-1, -2 or -3 database upgrades it transactionally to schema 5. Foundation records are preserved. Legacy coordinator snapshots upgrade from schema 1 through the existing schema 2 policy to schema 3: their original snapshot (including old receipts) is retained in an append-only migration event, while receipts without attempt authority are removed from the current snapshot using the stage policy below. Budgets, execution ownership, inbox and effect records remain intact; legacy pending receipt events cannot become valid new receipts. Ambiguous legacy continuation receives a named compatibility boundary; malformed snapshot structure fails closed. SQLite 0 means a fresh database. Storage schema 4 upgrades to 5 without changing coordinator snapshots or accounting. Schema 5 adds versioned duplex metadata to command records; previous readers must not own these commands. Versions other than 0 through 8 are rejected (schemas 6–7 added provider/stock records; 8 is the subscription boundary below). Previous readers reject newer schemas; downgrade is unsupported. Drain old processes and make an offline database backup before an operator chooses to open an existing database with this build. No retained environment database was migrated during this task. Tests construct owned v1 and v2 databases, migrate owned copies, verify preserved records and rejection by the exact previous readers (including ec9a0cd).

### Legacy snapshot continuation policy

Migration joins cancellation from the authoritative run row and legacy snapshot monotonically. A cancelled idle run stays `cancelled`; a cancelled run with an outstanding action stays `cancelling`. Saving any later snapshot also cannot clear authoritative cancellation. Neither migration nor cancellation releases a slot or alters the action/outbox reservation; only the existing quiescence path can settle ownership.

| Legacy state without outstanding execution                           | Migrated continuation                                                          |
| -------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| admitted, baseline                                                   | admitted; reserve and run a fresh bounded baseline                             |
| verifying, awaiting_delivery_evidence, handoff_ready                 | verifying; reserve and run fresh bounded checks                                |
| no_code                                                              | no_code, still excluded from coding success                                    |
| blocked, recovery_required                                           | retain the explicit blocker/recovery boundary                                  |
| waiting_external                                                     | retain reason/wake/deadline and map the saved resume stage by this same policy |
| cancelled, cancelling                                                | cancelled when idle; cancelling when an action remains                         |
| implementing without its action, missing/ambiguous wait continuation | named compatibility recovery boundary                                          |

Any noncancelled outstanding legacy action enters `recovery_required` with `legacy-execution-reconciliation-required-before-explicit-rerun`. Its exact execution identity, effect, slot and budgets remain unchanged. The current owner may interrupt or ingest/apply a trusted quiescence result to settle that action; the result cannot adopt code or authorize another dispatch across this boundary. Then explicitly cancel the old run and admit an authorized rerun, retaining its workspace/evidence for inspection. Migration never guesses whether an old implementation finished.

Revalidation spends from the original remaining elapsed/token allowance and does not reset any retry/repair counters. If that allowance is exhausted the normal budget blocker remains the result. Saved baseline and delivery-evidence waits resume at admitted and verifying respectively, so losing legacy receipts cannot strand them in a stage whose prerequisites are missing. The legacy wait bug (`resume=waiting_external`) becomes a named recovery boundary instead of an invented next step.

### Usage migration (Taskbot #71)

Schema 2 snapshots are structurally validated before upgrade. Their exact numeric `reportedTokens` becomes `budgets.legacyReportedTokens`; it is **not** provider-attested usage and is never added to `knownTokens`. Fresh runs have `legacyReportedTokens: null`; a migrated zero remains an explicit legacy zero. All other budget counters, input identity and outstanding action/effect/slot identity are preserved. The original snapshot is archived in the append-only migration event in the same transaction as the upgrade. A schema 2 handoff returns to verification with receipts cleared. Outstanding actions enter the same explicit reconciliation boundary described above. Authoritative cancellation always wins. A malformed snapshot rolls back the entire database upgrade.

Historical consumed inbox/effect/event payloads remain unchanged, including numeric result records. They are historical evidence, not new usage receipts. An unconsumed old numeric result is deliberately rejected by the new event validator: reconcile local quiescence through a fresh versioned usage result under a new inbox ID. It cannot adopt legacy output across the compatibility boundary. Downgrade and mixed old/new writers are unsupported.

### Direct-harness subscription budget mode (Taskbot #90)

Storage schema 8 adds an explicitly versioned, harness-neutral `subscription-observed-v1` run mode from the accepted contract `acceptance/subscription/**` at `572accf` (#88/#89). It is selected only by explicit admission, `budget: { mode: "subscription-observed-v1", reportedTokenThreshold }`, and is stored as coordinator snapshot schema 4. The snapshot schema is the immutable per-run mode. Admission without `budget` and every existing record remain the unchanged strict mode, snapshot schema 3 with `HardLimitsCapability` and provider-receipt usage. Opening an older database validates every stored snapshot, rolls back if any snapshot is malformed or forged, and leaves strict rows byte-identical. The previous 572accf reader refuses storage 8, and its snapshot validator refuses schema 4. No path changes a mode after admission: `revise` cannot carry budget fields, a changed version cannot claim the lease, and a subscription-mode rerun must name a terminal, quiescent previous run. Old unknown-success barriers and unknown counts stay with the old run.

A subscription run rejects any `HardLimitsCapability`. Its separate `qualification` is identity only: `{ schema: 1, id, harness, contractId, budgetMode, binding: sha256 }`, with no booleans and no accounting guarantee. A null qualification blocks agent work. Dispatch requires the transport's qualification to equal the run's qualification exactly, and a hard-limit capability on the transport is refused. This package ships no loader and no approved binding, so production subscription admission is still unavailable until a separately qualified, harness-specific binding exists (for example #95 for Claude Code, or #81 for codex exec).

Agent results report harness telemetry as `usage.schema: 2` with `source: "native-harness-telemetry"`, a harness name, and a sha256 `receipt` of the retained raw telemetry. The status is one of:

- `reported`, with `input`, `output` and the optional subsets `cachedInput`/`cacheWriteInput` ⊆ input and `reasoningOutput` ⊆ output;
- `ambiguous-zero`, for absent or all-zero telemetry;
- `unknown`.

The adapter normalises its native shape into these subset semantics: codex `turn.completed` usage, or Claude Code's final result usage. Per-message interim reports are not an action total. Reported input + output is added in full to `budgets.harnessReportedTokens`: it is never clipped to the planning charge, refunded, or merged with `knownTokens` (provider receipts, which this mode refuses) or with `legacyReportedTokens`. `ambiguous-zero` increments `harnessAmbiguousZero`, and `unknown` increments `unknownActions`. A claimed success with unresolved usage keeps the existing unknown-success barrier and does not adopt a head. Local (non-agent) actions must report `local-no-model` zero.

In this mode `limits.actionTokens` and `totalTokens` are only monotonic planning charges that bound the number of fresh agent actions. They are not token limits. Just before a new agent action is reserved (all agent work kinds, including CI repair), `schedule` stops with a `budget` blocker in two cases: any usage is unresolved (`subscription-usage-unresolved`), or accumulated reported usage has reached the threshold (`subscription-reported-threshold-reached`). No counter or charge moves when it stops. Verification, CI observation and cleanup continue within their own limits. Review exhaustion still cannot consume the reserved CI repair attempt, but reserved attempts do not promise remaining subscription quota. There is no hard aggregate token limit, no mid-turn cutoff and no overshoot bound. Tests live in `tests/coordinator-subscription-budget.test.mjs`, and evidence in `.qualification/subscription-budget-90/`.

## Execution capacity, waits and cancellation

There is exactly one durable execution slot across coordinator run IDs, distinct from each run lease. Reserving any action occupies it. Expiry or release of the run lease never frees the slot. The lease fence that reserved the action must still match at initial dispatch. A new owner may reconcile the recorded action, but cannot silently start it again. After an ambiguous/lost start response the effect stays `sending` and a second dispatch refuses.

Dispatch uses the maximum of the current clock and the snapshot's persisted observed-time high-water mark; clock rollback cannot reopen an already observed expired deadline. A trusted result for the exact action and input digest must attest quiescence before slot release; all foundation command records for that run must also be finished. A cancellation, version change, input revision, unquiesced result or deadline violation cannot authorize further work. Cancellation persists first; `interruptCoordinator` then calls the trusted transport's bounded interruption entrypoint. An interruption acknowledgement is not a completion receipt. Invalidated/late results may settle execution ownership but cannot adopt code or mint readiness.

External waits persist reason, wake time, deadline and resume stage before execution capacity is released. Quiescence still gates release. Successful code results during draining update the head and resume at verification. Noncoding completions retain the saved stage; repeated wait updates and receipts received during a wait also preserve a meaningful resume stage. Early wake refuses; deadline expiry records an access blocker. The same run/workspace resumes; it is not recreated.

## Budgets and evidence

Each run reserves one environment retry, two product/CI repair attempts with at most one usable by product repair, one review correction and one disagreement decision. CI observation and CI repair remain reachable after subjective review exhaustion. The total token and elapsed ceilings remain global and may independently prevent any action. Head/scope revisions do not reset counters. Repeated unchanged failure signatures and no-op repair results stop rather than looping.

Every action reserves elapsed allowance before dispatch; agent actions also reserve token allowance. Reservations are never refunded in this first implementation, including after crashes or cancellation. This deliberately conservative policy prevents double-spend. Known usage, unknown completed actions and legacy numeric reports are recorded separately from these charged reservations; none refunds allowance. Elapsed accounting uses a persisted high-water timestamp, so clock rollback cannot lower usage. Every dispatch has a deadline bounded by both its allowance and the total run deadline. Scheduler ticks can expose deadline exhaustion without dispatch. A reported hard-cap overrun is a recovery failure, not extra authorized budget.

### Versioned action usage

A result now contains `usage` instead of numeric `tokens`:

```ts
{ schema: 1, status: "known", tokens: 37,
  source: { kind: "provider-receipt", reference: "retained-accounting-receipt-id" } }
{ schema: 1, status: "known", tokens: 0,
  source: { kind: "local-no-model", reference: "owned-command-receipt-id" } }
{ schema: 1, status: "unknown", reason: "lost-provider-response" }
```

Known means complete actual usage for the **whole action** (input including cached input plus all output including reasoning, across every request). The trusted future adapter must resolve the retained source reference and validate its accounting evidence before producing this result. This small contract does not fetch or authenticate provider receipts; a string, flag or forged receipt cannot establish provider enforcement. `local-no-model` is permitted only for non-agent actions and only with zero tokens. A partial total, estimate or reserved allocation must never be submitted as known actual usage. Unknown has no numeric value; use it for missing/incomplete telemetry. Tests use explicitly synthetic references.

Settled known actions add to `budgets.knownTokens`; settled unknown actions increment `unknownActions`. These are separate from `reservedTokens` and the historical `legacyReportedTokens`. Therefore `knownTokens` alone is not the run total when unknown actions, legacy reports or outstanding execution exist. While draining, `executionUsage` retains the immutable observed usage; aggregation and slot release wait for verified local quiescence. The final usage record is retained in the durable effect receipt. Interrupt acknowledgement does not establish quiescence or remote completion. The full reservation stays charged regardless.

An unknown failed/interrupted result retains its normal bounded failure/recovery path. Later independently valid work may qualify even while the run's total actual usage remains incomplete; its hard bound is the nonrefundable reserved total. An unknown **claimed success** cannot adopt a changed head or reach no-code/handoff. Its work kind is retained in `unqualifiedResults` immediately on the first success claim, even while execution remains unquiescent. A later failed/interrupted drain cannot erase that claim; the barrier survives restarts, revisions and passing receipts. Only an independently valid successful result in that same semantic role clears it: implementation/product/CI/review repairs form the implementation role; review/arbitration form the review role; baseline/environment retry form the baseline role; other work kinds match exactly. An unrelated successful verification cannot qualify an unknown implementation. Existing stage, input, deadline, cancellation, repair-counter and evidence gates still apply; no new retry allowance or dispatch route is introduced.

Usage is immutable after its first observation, including during an unquiescent drain. Conflicting usage fails atomically. Exact replay of a settled result, even with a new inbox ID, consumes that duplicate without changing snapshot, accounting, effect receipt or capacity; a conflicting settled result is rejected. All replay still requires the current lease, version and issue ownership. Unknown, malformed or unsupported usage versions are rejected before mutation. A new producer must not reuse a historical inbox identity with a changed payload.

`HardLimitsCapability` and `CoordinatorTransport` are a **trusted integration seam**, not proof that any installed provider enforces a cap. Missing capability blocks admission; a changed capability/version blocks dispatch. The future harness must independently establish hard elapsed/token enforcement, synchronous start, no hidden retry, stable action identity, isolated authority, and complete process/tool quiescence. Merely setting these fields or receiving token notifications is not production qualification. No live transport is supplied here; tests inject explicitly labelled local contract transports.

Trusted collectors first call `beginCoordinatorObservation(lease, kind, collectorKey)` **before launching the attempt**, then bind that returned token into the hashed receipt's `observation` field. The stable collector/action identity must represent the actual attempt, not the arrival of a response. The coordinator durably increments that kind's generation and invalidates dependent readiness in the same transaction as recording the token. A lost reply or duplicate launch request with the same key returns the original token without advancing generation, changing revision or invalidating anything. Tokens are not reminted when delayed results arrive. A future CI adapter must map actual upstream workflow/job/attempt identity into this collector lifecycle; this local seam does not implement that platform mapping.

Review tokens bind the exact baseline/checks/CI evidence bundle (both observed generations and receipt references); approval additionally binds review. A newer attempt supersedes old tokens even before its result arrives. Registration and apply both reject superseded tokens or changed bundles. A token accepts one immutable result; a conflicting outcome/hash requires a genuinely new attempt, not a new inbox ID. Redelivery of the same receipt does not erase a later review. Tokens/history live in the existing SQLite coordinator receipt registry, and current generations in the versioned snapshot.

`registerCoordinatorReceipt` is only for trusted coordinator-owned check/CI/review/approval collectors. It reads the existing content-addressed `Evidence` artifact, validates referenced artifacts and exact scope/head/base/build/check-plan/coordinator-input binding, then registers a durable evidence event. Failure signatures and diagnostics availability are part of the hashed receipt. The apply transaction rechecks identity so a queued receipt cannot cross a revision. All dependent receipts invalidate on a head/scope/plan change; new checks/CI invalidate review and approval. Failed CI with unavailable diagnostics remains failed and has a repair route. Content hashes establish integrity, not producer identity: production isolation must keep this API, SQLite and evidence storage outside the agent write boundary.

`handoff_ready` means current local contract evidence has checks, CI and review passes. It is not a remote PR, merged change, tracker closeout or live acceptance claim. `no_code` is separate and cannot count as a coding handoff. There are explicit environment/access/hardware/capability/budget/engineering/recovery blockers.
