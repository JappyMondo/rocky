# Unattended delivery recovery

The September 25 run audit found three recurring gaps:

- ATT-777, ATT-842 and ATT-1079 repeatedly reached the frontend while the API capability check still failed. One capability probe caused teardown and a fresh install/start cycle, preventing a slow backend from settling.
- ATT-764 and ATT-842 recorded blocked UI sweeps (first-time setup, missing local fixtures and reachability). Recovery restarted services but never handed the actual diagnostic evidence to an agent.
- ATT-920 retained uncommitted implementation work and failed at PR delivery. Agent completion did not imply a deliverable commit.

The default workflow now waits for executable environment assertions within the configured service readiness attempts and command timeout. It keeps the owned service processes alive while waiting. Access, unsupported and product blockers are not treated as startup delays. The probe remains one journaled process step, preserving older journal ordering.

New run snapshots carry `settings.recoveryVersion: 1`. They allow at most two environment diagnosis/repair calls per delivery attempt, separate from product review limits. The connected implementation agent handles baseline setup; the connected fixer handles UI prerequisites. They receive repository configuration, the exact blocked check notes and existing verification context. They can repair local worktree prerequisites and select configured commands for host execution. Manual commands and their manual prerequisites remain forbidden. Missing external permission or authority remains a blocker.

Selected setup commands run through the same dependency, endpoint and executable-verifier boundary as ordinary provisioning. A UI repair sends the run back through validation and review before another full UI sweep. An agent's repair claim never supplies verification evidence. The extra validation cycle does not consume the final product-review allowance.

Uncommitted delivery work returns to the connected implementation/fixer agent up to twice. Rocky checks status again before opening/pushing PRs. It never discards work or blindly commits it to clear the gate. Compliance review still checks whether the requested implementation is complete.

Existing frozen snapshots without the recovery version keep their original control flow. Installing this runtime does not rewrite old snapshots, approve checkpoints or restart failed runs. New snapshots enable recovery even for previously saved profiles. Service readiness polling also benefits older snapshots because it adds no journal steps.

Regression coverage uses project-neutral real services and temporary worktrees: delayed capability readiness, local fixture repair through the host catalog, repair replay without duplicate agent calls, unfinished commits, bounded failure, pre-recovery snapshot replay, and CI-fixer reachability before review exhaustion. Build/distribution checks cover the installed package separately from source tests.

The final live audit also exposed ATT-893 failing a compliance review because optional Chrome preparation failed, and ATT-1098 receiving CI cleanup output instead of the original diagnostic, followed by a Linear activity readback mismatch. Browser-only startup errors now leave non-browser agents operational, with an explicit blocked-coverage instruction; cancellation still stops preparation. Failed-job logs retain bounded early error context alongside the final log lines. New recovery-version runs fence unresolved complaint JSON with a collision-safe Markdown fence so Linear cannot interpret embedded log fragments as links or formatting. These paths have deterministic regression coverage; existing persisted mismatched Linear effects are not rewritten.

The full suite additionally reproduced a preflight deadline race: the remaining-budget timer could fire before the overall abort signal, but its shorter duration was compared to the original duration as an error string. A typed timeout now preserves the correct diagnostic regardless of elapsed setup time; the test explicitly advances the deadline calculation.

The live verification after quota renewal found a CI fixer that created an empty commit but returned `retry`. Rocky retried the old remote SHA and exhausted its allowance while leaving the commit local. New snapshots now carry `ciRetryVersion: 1`: a retry first synchronizes actual local work across the delivery repositories, then returns changed revisions through validation and review. Only unchanged revisions request a CI retry. Older snapshots preserve their original step order. A regression checks both paths and journal replay, including an agent that returns the wrong action label.

The same verification showed external check failures being sent through an Actions-only retry adapter. GitHub retries now also rerequest failed check runs through the Checks API, preserving current-head and open-PR checks. A retry with no supported target reports refusal instead of success. New-version coordinators pass a refused retry back to the bounded CI fixer with the precise integration evidence; permission denial cannot masquerade as a successful retry or cause an unbounded loop.

A fresh real run then reproduced branch occupation by a retained failed workspace. Workspace creation now reads Git's NUL-delimited worktree records, verifies both run headers and the exact Rocky-owned repository path, and transfers a terminal same-issue worktree with `git worktree move`. This preserves unpushed commits, staged changes, untracked files and ignored local fixtures without duplicating large dependency trees. Active, unknown and other-issue owners remain protected. Real-Git tests cover English/German environments, retained dirty state, unsafe owners and idempotent replay. This stays inside the existing workspace step, so journal step order does not change.

The retry preflight now permits retrying a failed initial workspace allocation without a completed workspace receipt, provided no later workflow step has begun. It still requires the retained snapshot and execution metadata and rejects incomplete later journals. Partially allocated worktrees must still be on the issue branch before reuse.

Manual runs now receive the parent-IPC checkpoint adapter even without a Linear agent session. Questions and approval checkpoints park and resume durably instead of crashing; Linear effects still require their session identity. The parent creates durable local controls without remote elicitation or polling when no session is owned. Regression coverage exercises both checkpoint kinds with and without Linear and resumes each recorded answer.

New admissions carry prior recorded human question answers in `issue.clarifications`, scoped to the same issue URL, identifier, lead repository and profile. The immutable issue snapshot retains question, answer, source run/step and timestamp in chronological order. Approval checkpoints, unanswered questions and agent summaries are excluded. The refiner receives an explicit reuse policy; newer human instructions supersede historical scope, and historical answers never authorize a new merge. Existing frozen runs and journal order are unchanged.

New snapshots also carry `scopeCommentVersion: 1`. After refinement, the complete scope decision record is published through the idempotent ticket-comment adapter before planning or implementation. This makes decisions and clarification answers visible to later runs through normal issue comment hydration. Older snapshots retain session posting and their original journal positions; tests replay both sides of the boundary and ensure the comment is not duplicated.

Manual issue runs now resolve and persist their real ticket identity before receiving issue comments, state changes and SCM services. They do not fabricate an agent session: explicit posts use idempotent ticket comments, while agent-session activities remain unavailable. Existing manual journals keep their original prefix. Configuration command tests remain local-only.

The explicit `rocky_run_restart` control starts the latest failed or exhausted issue using a current workflow snapshot and fresh ticket comments while retaining its issue branch. Old journals remain unchanged, prior human question answers are hydrated at admission, and old merge approvals are not copied. Request IDs make repeated calls return the same successor; live, cancelled, successful, stale and superseded runs are refused. This is the migration boundary for previously failed runs whose frozen workflow predates recovery fixes.

Adopting an existing ready pull request now honors `openPr({draft: true})` before returning its handle. This prevents the ready-PR report hook from running before validation and UI provisioning. The draft transition stays inside the existing SCM operation, so already recorded ready handles preserve their original report steps on replay. Regression coverage includes both a fresh adoption and an explicit pre-change journal.

New snapshots carry `recapEnvironmentVersion: 1`. Before visual recap capture, the workflow restores the service selection and capabilities established during UI validation, provisions and verifies them through the host catalog, and passes their actual endpoints to read-only capture agents. It always stops owned services after the report. Environment failures use the existing bounded repair path and return through validation. Pre-version snapshots add no provisioning steps; a project-neutral live-server regression checks capture reachability and replays both journal versions without duplicate captures.

A later live pass exposed a transient Linear 503 during startup and a Codex final answer with an unfinished shell search. Query-only HTTP retries now cover bounded 5xx responses as well as connection errors; ambiguous mutations still require their existing durable readback. An unfinished Codex turn retains its owned session as a typed continuation request after process cleanup. The agent runtime records a bounded reconciliation nudge under the original attempt deadline, resumes that session, and requires a fresh valid result. It neither accepts unfinished checks nor restarts completed implementation immediately. No positional journal steps or old snapshot contents change.

Validation commands can themselves require service endpoints before UI review. New snapshots carry `validationEnvironmentVersion: 1`: the validation stage collects endpoint references from the selected command dependency closure, provisions and verifies those services through the existing environment manager, then executes the checks and stops owned services in a `finally` block. It does not require a browser capability for a backend-only check. Provisioning blockers enter the existing bounded environment fixer instead of escaping as a missing-endpoint exception. Frozen snapshots without this flag keep their original positional steps; previously failed runs need a fresh snapshot via restart. Regression coverage includes dependency ordering, unselected services, the old snapshot boundary and the environment repair route.

Planned daemon shutdowns previously counted as interrupted Boots in the crash-loop guard. Repeated package installations could therefore fail a healthy long-running agent. After owned workers stop, the scheduler now records the last intentionally stopped Boot in a non-positional journal control. Serial and nested parallel replay count only interruptions after that boundary. Unmarked crashes keep the existing three-Boot limit; terminal outcomes are never rewritten. Regression tests resume four successive planned interruptions, retain agent session progress, and exercise the original crash-loop tests.

Agent progress also distinguishes planned stops: streamed events persist the owned session, and replay resumes that session without consuming an agent attempt or extending its deadline. If shutdown happened before a session was available, the retained attempt starts in the same workspace. Existing unmarked interruptions retain their retry policy.

An edit-capable agent that reports a valid blocked envelope now has one durable diagnostic continuation in its existing session, bounded by the existing nudge allowance and original deadline. The prompt distinguishes a failing or hanging repository command from missing authorization, credentials, hardware or tools; unavailable access is never invented or bypassed. Read-only and malformed blockers still fail immediately, and a repeated blocker remains terminal. Tests cover recovery, repeated blockage, missing grants and four planned agent interruptions without spending its attempt budget.

Service liveness rechecks use the configured readiness attempts and interval, bounded by the provisioning deadline. A transient timeout or non-success response does not immediately invalidate a replayed success. Polling stays inside the existing recheck receipt, preserving pre-change journal order. Persistent failures still fail closed. Generated launchd units allow 60 seconds for owned process cleanup and interruption journal flushing.

Agent validation handoff distinguishes configured host commands from agent-owned checks. A sandbox denial for an existing non-manual catalog command is reported as pending host validation with its command ID, rather than an unavailable-tool blocker. The workflow still selects commands and records their real exit results; manual and unconfigured operations receive no additional authority. Additional acceptance checks remain the agent responsibility. This instruction-only correction inserts no journal steps.

Environment repair results select only IDs from the non-manual command catalog. On replay, older receipts that also named a known service omit that service from setup commands; the existing environment provisioning path still starts and verifies it. Unknown IDs and manual prerequisites are never silently authorized.

Finished clean worktrees are released once their HEAD is confirmed on a remote branch. Cleanup preserves root evidence files, unknown directories, dirty worktrees and unpublished commits. A failed run retains its repository for retry; an orphaned recognized package cache left after transfer is reclaimed. The scheduler retries terminal workspace cleanup every five minutes, including after daemon restart.

New working Boots wait in the queue when free disk space falls below `concurrency.minFreeDiskGiB` (5 GiB by default). The queue records the reason and resumes automatically on a subsequent scheduler tick when storage recovers. Existing work is not interrupted, so the reserve is an admission guard rather than a disk quota.

New delivery snapshots set `uiFixtureVersion: 1`. Before each UI inspection, a preparation agent resolves every planned check to a local fixture, repeatable navigation instructions, an existing repository source reference and browser screenshot evidence. It can request only configured non-manual setup commands; their dependencies are checked before host execution. Setup is followed by a fresh preparation pass. Local prerequisite recovery is bounded to three preparation calls and does not spend product review attempts. Missing external access remains an explicit blocker, never a visual pass. Changed tracked source returns through push and validation before inspection.

Prepared fixture paths are relative to the current verified UI service, avoiding stale ports after restart. Screenshots must resolve inside the run evidence directory. The independent UI inspector receives these fixtures and must still execute the actual checks. Old snapshots omit the version and replay their existing planner/inspector sequence unchanged; use a new snapshot to opt an exhausted historical run into preparation.

ATT-1089-4 exposed an external check retry that GitHub answered with HTTP 404. The check remained failed because its provider reported no available upstream accounts. New snapshots carry `ciRetryRefusalVersion: 1`: after the CI fixer receives a retry refusal, another `retry` decision with no changed revision ends that attempt instead of sending the same request repeatedly. A changed revision still returns through validation. GitHub check-run HTTP 404 is reported as an unsupported retry with the check ID and provider-access guidance. Older snapshots retain their original step sequence; tests replay both sides of the boundary. Neither a refused retry nor local checks count as passing CI.

ATT-764-4 reached its first fixture preparation but failed while validating the agent result: the agent returned a valid `setup` object with a `summary`, and the generic agent wrapper removed that field before applying the discriminated-union schema. The wrapper now keeps `summary` when every union branch declares it. Strict object schemas still receive the separate injected summary. This changes no journal position; the retained failed agent Step can be retried after installing the runtime. A regression runs the real agent result wrapper with a union-shaped setup result.

The next ATT-764-4 retry exposed a separate prerequisite: fixture preparation was asked to capture screenshots in the Run evidence directory, but that directory did not exist and was outside the edit agent's writable roots. The fixture call now opts into a Run-owned screenshot write grant. The agent runtime creates the directory before invocation and adds only that directory to its writable roots. Other edit agents retain their prior grants; read-only agents retain evidence read access. This adds no positional journal Step and has a focused grant regression.

## Completion and replay repairs after the live run audit

ATT-776-1 reached `completed` even though its recap decision said the comment and issue closure were unverified. The old comment workflow wrote the recap before publishing the comment and moved the issue only to its review state. New snapshots carry `commentDeliveryVersion: 1` and `recapDecisionVersion: 1`: Rocky publishes the reviewed comment, generates a recap that can inspect that publication, requires a `ready` decision, then closes the issue and reads the selected Linear state back. A missing or non-ready decision ends the run as exhausted and leaves the issue open. PR delivery likewise routes a non-ready recap decision through its existing fixer before marking a PR ready. The frozen snapshot flag selects the comment sequence, since a new journal can resume inside `reviewReport.*` too. The old sequence remains replayable and is covered by an old-journal test.

ATT-893-2's planner had saved `localhost:4201` in its check URL; after a restart, another run served that port. New snapshots carry `uiPlanEndpointVersion: 1`, requiring planned check URLs to be relative to the verified UI service. For existing plans, Rocky binds local loopback URLs and instructions to the current verified endpoint before inspection. External URLs remain untouched. Fixture preparation now receives the validation ownership and repository catalog handoff that its blocked report said was missing. This does not establish that every requested component preview or browser interception tool works; the retained run must still pass an independent sweep.

ATT-920-2 had a previously successful install receipt, but a later Boot reran that installer after the fixer had modified source. The changed source failed compilation before the fixer could continue. Replaying a successful setup probe now consumes its recorded background Step at the same journal position without starting the installer; fresh capability verifiers still execute. A later background restart failure can leave an earlier failed Step before a waiting fixer Step, so retry selection reopens that failed setup Step first. This is restricted to an environment probe with an earlier successful receipt and the matching setup failure. The old journal retains its original bytes and Step order.

ATT-764-4 reached its fixture preparer again after the setup repair but finished exhausted because its resource People route stayed loading and several role/header states had no supported preview. `uiFixtureRecoveryVersion: 1` on new snapshots routes a still-blocked fixture preparation through the existing bounded environment fixer. That fixer can repair local seed, role and preview prerequisites, then Rocky pushes and revalidates changed source before another UI sweep. Old snapshots retain the direct blocked outcome and their positional journal sequence. A project-neutral integration exercises both sides of this boundary; it does not claim that the affected Attraccess states are reachable yet.

ATT-920-2's next CI run exposed a GitHub log-excerpt defect. The failed plugin job contained a concrete audit assertion, but earlier setup warnings filled Rocky's bounded evidence buffer before the failure. The SCM reader now keeps bounded recent windows for strong failure markers separately from weaker warnings, then includes the final log suffix. A project-neutral regression covers setup-warning saturation and ANSI-formatted assertions; a temporary test against the actual 181 KB job log confirmed the 200-line excerpt contains the failing test and expected/received counts. The earlier failed-job receipt is immutable; new SCM reads use the repair.

ATT-1098-3 repeatedly failed the configured plugin check under Nx, while a fixer reran two narrower Jest suites serially and the next command-selection agent could omit the failed catalog command. New snapshots carry `validationRecheckVersion: 1`: failed and prerequisite-skipped configured command IDs remain mandatory in the next validation round, regardless of later optional selection. Only a zero exit from that configured command clears its pending ID. A source fix therefore returns through the same real check, and repeated failure reaches the existing validation cap instead of a false pass. Old frozen snapshots keep their prior positional sequence; tests cover new and old selection behavior, snapshot opt-in, and replay of a pre-change journal.

ATT-764-5 exposed another fixture recovery boundary: an agent can return the validated `<blocked>` envelope, which the harness raises as `AgentBlockedError` instead of returning the fixture schema's `blocked` result. That exception previously failed the run before the bounded fixture and environment repair paths. When `uiFixtureRecoveryVersion: 1` is present, fixture preparation converts a valid agent blocker to the same structured blocked result, preserving environment retry and the human access categories. Malformed blockers still fail visibly. Older frozen snapshots retain their former exception path; tests cover both sides of the boundary.

Fresh installations admit one Run at a time by default. Repository checks can spawn their own workers; overlapping full build and test commands saturated an eight-core host and produced unreliable timeouts. Operators can raise the explicit cap for hosts with capacity. A Run's diagnostic logs now belong under `workspace/.rocky-evidence`, alongside the repository worktrees. Agent validation and uncommitted-work repair instructions name that location so the evidence is retained without leaving untracked logs that block PR delivery.
