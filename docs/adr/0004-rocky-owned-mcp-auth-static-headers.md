# Rocky owns MCP OAuth, injecting tokens as static headers

Both shipped Harnesses have their own MCP OAuth machinery (`claude mcp login`, `opencode mcp auth`), so the obvious path was to lean on it. It doesn't survive contact: neither CLI runs the browser dance headlessly, neither token store is injectable from outside (Claude Code's lives in the OS keychain), the two stores drift independently, and opencode doesn't even read `.mcp.json` — it wants its own `opencode.json` shape behind an `OPENCODE_CONFIG` env var. The MCP spec (OAuth 2.1) defines no third-party token handoff; the one seam both CLIs share is a static `Authorization` header on a remote server ([NG-583](https://linear.app/digimondo/issue/NG-583)).

So Rocky owns the whole lifecycle: `rocky mcp login <server>` runs the OAuth flow outside any Run, tokens live URL-keyed and machine-global in `~/.rocky/credentials.json`, are refreshed silently whenever an adapter renders config for an attempt (never mid-attempt), and reach each Harness as a pre-obtained Bearer header in the per-Step config the adapter translates from `.rocky/mcp.json`. A useful side effect: a static header disables Claude Code's own OAuth fallback, so a rejected token fails deterministically instead of degrading. Consequence: a Run reaching a server with no working token is Run-fatal at that Step, naming the login command — a Checkpoint the Workflow never wrote would be the framework smuggling in an opinion — and Preflight checks refreshability of stored tokens at Run start so stale credentials fail in the first minute.
