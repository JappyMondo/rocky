# CONTEXT

Glossary of the agent-rocky-reviewer domain. Terms are canonical: use them exactly as defined here in code, tickets, and UI copy.

## Terms

- **Rule**: One short prose review instruction with a handle: id, status, provenance (`bootstrap` / `learned` / `manual`), timestamps. The LLM consumes only the prose; the metadata exists so the UI and Learnings can point at individual rules. Rules are always per-repo.
- **Rule status**: `active`, `disabled`, or `tombstoned`. Tombstoned rules are never deleted and never re-proposed; there is no true deletion.
- **Tombstone**: A rejected, reverted, or user-deleted rule kept as a "do not re-propose" record. Fed to the Learning pass only — never to the Review prompt.
- **Bootstrap**: The one AI pass at repo-install that mines the checkout (structure, commit history, existing agent docs like CLAUDE.md / CONTRIBUTING) and proposes the initial rule set. The user confirms it with per-rule checkboxes as a step of the add-repo flow; reviews start only after that step.
- **Review prompt**: Plain concatenation of the global, user-editable system prompt plus the repo's active rules. No templating. Tombstones and noise instructions are not part of it.
- **Feedback**: Replies to Rocky's comments and 👍/👎 reactions on them. Thread-resolution is never a Feedback signal (it never mutates a rule) but it is a Review verdict signal. Only feedback from authorized authors mutates rules.
- **Authorized author**: A user whose feedback counts for learning: has write access to the repo, adjusted by the repo's optional author whitelist (adds non-write users) and blacklist (mutes write users).
- **Feedback sweep**: The single API fetch at PR/MR merge or close that collects all Feedback on Rocky's comments in that PR. No live feedback ingestion, no reaction polling during the PR's lifetime.
- **Learning pass**: The batched AI pass run on a Feedback sweep. It may create, edit, disable, or leave rules unchanged ("if they are fine, they are fine"), filters noise and nitpicks, and receives Tombstones to avoid re-proposing them. Changes auto-apply.
- **Consolidation pass**: A weekly AI pass per repo that merges overlapping rules and prunes redundancy. Skipped when no rule changes happened since the last run. Its changes are ordinary Rule changes in the Learnings.
- **Rule change**: One append-only audit record: rule id, action (`created` / `updated` / `disabled` / `reverted`), old text → new text, one-line AI rationale, cause (SCM permalinks to the PR and feedback that triggered it, or "bootstrap" / "consolidation"), timestamp.
- **Learnings**: The web UI view rendering the Rule change log, newest first, grouped by PR — "how each piece of feedback shaped the rules". Each entry offers one-click revert.
- **Review run**: One execution of Rocky's review against a PR/MR head. States: `queued` (debouncing), `running`, then exactly one of `completed` / `failed` / `superseded` (a newer push replaced it) / `cancelled` (PR closed). A run interrupted by a service restart returns to `queued` and re-runs from scratch against the current head; runs are never resumed mid-flight. There is one review mode: every run sees the full PR diff, with Rocky's open comments passed as prior context ("resolve what the push addressed, don't repeat the rest"). A run comprises the review step and, when a Ticket reference exists, a parallel Requirements step; results are always delivered together.
- **Trigger**: An event that starts a Review run: PR/MR opened, real code push, marked ready-for-review, re-request (Rocky requested as reviewer), an `@rocky review` comment from an Authorized author, or the resolution of the last open Finding thread. Draft PRs are skipped unless commanded. Pushes are debounced; a push during a running review supersedes it (cancel and restart). Resolve-triggered runs are capped at 3 per head commit, reset by any push; once exhausted the verdict is recomputed without a re-review.
- **Approval gate**: The hold on fork PRs from non-authorized authors: each push waits, unreviewed, until an Authorized author comments `@rocky review` — approval is per push, never per PR. Same-repo branches and forks of Authorized authors are never gated.
- **Report-only check**: Rocky's check states "a review ran", never "the code is bad". Findings never fail the check; internal errors never block a merge. The only merge-holding state is pending while a run is active, and only in repos that opt into Merge-wait.
- **Merge-wait**: Opt-in repo-side configuration (offered during the add-repo flow) that makes a merge wait for a running Review run to finish.
- **Thread conversation**: Rocky replying on his own comment threads like a human reviewer: answers any human's question, asks for clarification when a discard is ambiguous, and resolves a thread only on a confident discard from an Authorized author or when a push addresses the finding. A human resolving the thread in the SCM UI counts just the same: any transition of a Rocky thread to resolved closes its Finding. Capped at 5 Rocky replies per thread; bot comments are never answered.
- **Provider**: An AI backend Rocky runs Review runs through. Exactly two exist: the Claude Code CLI and the opencode CLI — both agentic harnesses that browse the checkout themselves. Any OpenAI-compatible endpoint (OpenAI, OpenRouter, Ollama, self-hosted) is reached by pointing opencode at a custom base URL, so it is configuration of a Provider, never a Provider of its own. Configured and authenticated at instance level; the active provider and model are an instance-global default with an optional per-repo override. Rocky never emulates a capability a Provider lacks — it says so instead.
- **ReviewResult**: The one canonical structured result every Provider returns from a Review run: a Review summary plus findings (file, line range, Severity, comment body, optional replacement text for an Applicable suggestion) and thread resolutions. Providers never touch the SCM; Rocky's server does all posting.
- **Finding**: One review comment Rocky raised: file, line range, Severity, body, optional Applicable suggestion. Two or three sentences of plain prose — what is wrong and why it matters — with no persona and no template. A Finding must name a concrete consequence; a Finding about the change's effect on an unchanged file anchors to the changed line that causes it and names the affected file in the body. Born in the Review run that posted it but owned by the PR/MR for its whole life — its thread outlives the run, later runs see the PR's open Findings as prior context, and it closes only when a push addresses it or a Thread conversation ends in a confident discard.
- **Severity**: One of exactly three values on a Finding: `issue` (correctness, security, data loss, a broken contract, or a Rule violation with a real consequence), `suggestion` (a genuine improvement, but nothing is wrong as written), `nit` (cosmetic or preference). Rendered as a bold word at the start of the comment body, because neither platform has a native severity field. It is load-bearing, not decorative: the Severity threshold reads it to decide whether the Finding is posted at all and whether it holds the Review verdict.
- **Severity threshold**: The Severity floor, an Instance setting with a per-repo override, default `suggestion`. One knob with two effects: a Finding below it is never posted and never affects the verdict (it becomes a Withheld finding); a Finding at or above it is posted and, while its thread is open, forces `request changes`.
- **Withheld finding**: A Finding below the Severity threshold. It is recorded in the ReviewResult and rendered in the report, never posted as a comment — so it can never attract Feedback and never reaches the Learning pass. The Review summary states how many were withheld.
- **Inline cap**: The maximum number of Findings Rocky posts as comments in one Review run (Instance setting, default 15). Enforced in the posting layer, not merely requested of the model. Findings dropped by the cap are report-only, noted as a themed line in the Review summary, and re-raised by a later run as earlier threads close.
- **Applicable suggestion**: The optional replacement text on a Finding, rendered by the server as the platform's one-click-apply block — GitHub's plain `suggestion` fence, GitLab's offset form. Emitted only when the range is contiguous, inside the diff and under a size limit; otherwise it degrades silently to a plain code block, since a reader is served by the fix and not by an explanation of our plumbing. Providers supply the replacement text and never the fence.
- **Review summary**: The prose Rocky writes once per Review run, delivered as the review body that carries the Review verdict, and the one place the raccoon persona is allowed — a few sentences on what the change does and his read on it. Everything factual around it is assembled by the server, never written by Rocky: the verdict line, Severity counts, a bulleted list of the `issue`-severity Findings linking to their comments, the withheld count, the Requirements section, and the Public report link. The Nudge comment carries a lighter version of the same warmth; the Overtime comment, error text and Thread conversation replies are plain.
- **Soft timeout**: The point (default 15 minutes) where a step of a Review run keeps running but Rocky posts the Overtime comment. Applies per step. Instance-global setting.
- **Overtime comment**: Rocky's PR comment at Soft timeout asking whether to kill and restart the run, carrying a link to the run's page and accepting an `@rocky restart` reply from an Authorized author. Edited to say so if the run finishes on its own.
- **Hard timeout**: The point (default 45 minutes) where a still-running step of a Review run is killed and its run marked `failed` with no automatic retry. Applies per step. A new push or `@rocky review` starts a fresh run. Instance-global setting.
- **Retry policy**: How many automatic retries a crashed step of a Review run gets (non-zero exit or invalid output) before the run is marked `failed`. Applies per step. Default 1; global setting with per-repo override. Hard-timeout kills are never auto-retried.
- **User**: A person's account on the Rocky instance. Sign-in is OAuth-only via a linked Identity — no password accounts. Lifecycle: `pending` → `active` → `deactivated`; users are never hard-deleted (Rule changes reference their feedback). Every active User sees every repo on the instance.
- **Identity**: One linked SCM login on a User: an issuer (GitHub, or a specific GitLab instance URL) plus that issuer's user id. A User may link several; signing in with any of them reaches the same account.
- **Pending user**: A freshly signed-in User awaiting activation by an Admin, who also assigns the role. Sees only a waiting page. The first User ever to sign in skips this and becomes Admin. Distinct from the Approval gate, which holds fork-PR pushes.
- **Admin**: The role holding the dangerous knobs: system prompt, Provider config and secrets, CLI updates, timeout/retry/concurrency settings, MCP connections, user management, repo add/remove.
- **Member**: The default role: everything an Admin does not reserve — viewing runs and reports, editing/disabling a repo's Rules, reverting Rule changes in Learnings, cancelling and re-running Review runs.
- **Public report link**: The unguessable per-run URL rendering a read-only view of a Review run's report and findings without sign-in, Withheld findings included and marked as not posted — "internal" means "not a PR comment", never "secret". Never expires; posted into the PR/MR (it is the GitLab check's link target, since GitLab checks cannot carry the report).
- **PAT**: A personal access token for the Rocky API, minted by a User on their profile. Carries the owner's role — no scopes; optional expiry (default never); shown once; revocable by the owner or an Admin. The API docs (OpenAPI + Swagger UI) are public; API calls require a session or a PAT.
- **MCP connection**: One tracker/MCP server Rocky can consult for the Requirements step: a preset (Jira, Linear) or a custom server (stdio command or HTTP/SSE URL). Instance-global, Admin-managed, authenticated via the web UI by OAuth grant (auto-refreshed) or API key. Carries a global enabled flag with a per-repo override — a globally disabled connection can be enabled for one repo — plus a ticket key pattern and a health status (a failed fetch or refresh marks it unhealthy).
- **Ticket reference**: A tracker ticket associated with a PR/MR: detected by matching each enabled MCP connection's key pattern against branch name, PR/MR title, and description (never commit messages), or linked manually by an Authorized author mentioning `@rocky` with a ticket key or URL. A manual link re-runs only the Requirements step.
- **Requirements step**: The isolated second agent invocation inside a Review run, parallel to the review step. It fetches every Ticket reference through only the matched MCP connections and judges whether the change meets the ticket, with the checkout and diff at hand. Per-ticket verdict: met / partially met / not met / couldn't assess. Lands as its own Requirements section in the report; fetch or connection failures are reported honestly and never fail the run.
- **Nudge comment**: Rocky's single per-PR comment — posted once, edited in place — when no Ticket reference is found on a repo with at least one enabled MCP connection, explaining how to link a ticket via `@rocky`. Never posted on repos without enabled connections.
- **Ticket required**: A per-repo toggle (default off) making "no Ticket reference" withhold the Approve verdict.
- **Review verdict**: The PR/MR review state Rocky submits with each delivered Review run: `request changes` (any open posted Finding thread at or above the Severity threshold, or any Ticket reference judged not met or partially met), `approve` (no such thread, every step succeeded, and every Ticket reference judged met — or none referenced with Ticket required off), or `comment` (anything else: a step failed, timed out, or a ticket couldn't be fetched). Findings below the threshold never affect the verdict, and neither do Withheld findings or findings dropped by the Inline cap — the verdict is computed from open posted threads only, so every objection holding a PR is one a human can read and clear. Distinct from the Report-only check, which stays an execution signal; whether a verdict blocks merging is repo-side configuration (branch protection / GitLab approval rules), never Rocky's doing. A downgrade revokes the prior approval; where GitLab lacks the request-changes state (pre-17.2) Rocky degrades to `comment` and says so in the report.
- **SCM platform**: One SCM host Rocky is connected to, at instance level: the GitHub App, or one GitLab instance's OAuth app plus webhook configuration. It is the issuer standing behind an Identity and the credential Rocky posts through. Several coexist (GitHub alongside N GitLab instances); the first is configured in the Setup wizard, every later one by an Admin.
- **Deploy config**: The handful of values fixed at container start and held nowhere else: the secrets encryption key and the public base URL (both required), plus the listen port and log level. It exists only for what is needed before the database is usable — the key that decrypts the store, the URL that cannot be inferred without a browser, and logging that starts before either. Nothing else is ever configured this way. Unrelated to Bootstrap, which is an AI pass.
- **Instance setting**: A configuration value held in the database and edited by an Admin in the web UI: system prompt, timeouts, retry default, concurrency cap, default Provider and model, Severity threshold, Inline cap. Every setting has exactly one home — an Instance setting is never also settable through Deploy config.
- **Setup wizard**: The unauthenticated first-boot screen that configures the first SCM platform, the one thing that must exist before OAuth-only sign-in can work at all. Guarded by the Setup token, and served for as long as the instance has no active Admin, so wrong credentials can always be corrected rather than locking everyone out.
- **Setup token**: The random token printed to the container's log on every start while the instance has no active Admin, and required to open the Setup wizard. Held in memory only and regenerated each boot, so it never reaches disk and is gone once setup completes; recovering it means restarting the container.
