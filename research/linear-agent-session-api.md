# Linear Agent Session API: activities, elicitation, webhooks, attachments

Date: 2026-08-28
Sources: primary only — Linear developer docs (`linear.app/developers`), Linear's published GraphQL SDL, Linear's OAuth app manifest JSON Schema, Linear's changelog, and the Cyrus source (`github.com/ceedaragents/cyrus`) where it evidences undocumented behaviour. Linear's developer doc pages carry **no publication or revision dates**; every `linear.app/developers/*` claim below was read on 2026-08-28. Introduction dates come from the dated changelog. Schema quotes are from the SDL Linear itself points coding agents at: [`packages/sdk/src/schema.graphql`](https://raw.githubusercontent.com/linear/linear/refs/heads/master/packages/sdk/src/schema.graphql) (master, fetched 2026-08-28).

**Status caveat that colours everything below:** the agents API is not GA. "Linear for Agents APIs are currently in active development and available as a Developer Preview. Functionality and Agent APIs may change before general availability" ([Getting Started](https://linear.app/developers/agents)). Agent Plans are additionally "in a technology preview", and the app-management mutations are `[ALPHA]`.

**TL;DR** — Linear gives Rocky more than the map assumed on three axes and less on one. Confirmed: a real session lifecycle with six states, a **native `awaitingInput` state** that Linear enters automatically when the agent emits an `elicitation` activity, a `select` signal that renders clickable options, and an `auth` signal that renders a **button to an arbitrary external URL** — which is precisely the affordance a Checkpoint needs, so Checkpoint can be a one-line elicitation in Linear plus the real UI in Rocky's local web app, with no emulation. Also confirmed: the agent's own token can move issue state, and Linear's best-practices page *tells* agents to do it. The acknowledgement deadline is **10 seconds** from the `created` webhook (and separately, the webhook HTTP response must return within **5 seconds**); the session goes `stale` after **30 minutes** without an activity, and stale is recoverable. Different than assumed: images cannot be posted *as* an activity — there is no image activity type; the only route is a Markdown `![](assetUrl)` inside a `body` field after a two-step `fileUpload` + presigned `PUT`, and whether the activity stream renders that image is **undocumented**. Attachments are link cards with a **20x20px, max 1 MB** icon — they cannot display a screenshot. Impossible: an agent cannot create a `prompt` activity (only humans can), cannot edit or delete an activity, cannot set session status directly, and cannot force a session to block. Decisive for the daemon: an OAuth app's webhook URL lives on the OAuth *client*, not on a per-workspace webhook record, and the only public way to change it is the Linear settings UI — the `oauthApplicationUpdate` mutation that would let Rocky re-point its own tunnel is `[ALPHA]`, undocumented outside the SDL, and only works on apps that were themselves created by a *managing* OAuth app. Rocky's ephemeral-tunnel assumption does not survive contact with this API without either a stable hostname or the ALPHA app-management path.

## 1. Agent sessions: entry point, webhook shape, lifecycle, acknowledgement

**How a delegated issue reaches the agent.** "Agents behave similar to other users in a workspace. They can be @mentioned, delegated issues through assignment, create and reply to comments, collaborate on projects and documents" ([Getting Started](https://linear.app/developers/agents)). Crucially, "Assigning an issue to your app now sets it as the **delegate**, not the assignee—so humans maintain ownership while agents act on their behalf" (ibid.); the schema has `Issue.delegate: User` — "The agent user that is delegated to work on this issue" ([SDL](https://raw.githubusercontent.com/linear/linear/refs/heads/master/packages/sdk/src/schema.graphql)). "Sessions are created automatically when an agent is mentioned or delegated an issue" and "Session state is visible to users, and updated automatically based on the agent's emitted activities. No manual state management is required" ([Getting Started](https://linear.app/developers/agents)).

**Webhook shape.** "The most common entry point is delegation—when a user assigns an issue to your agent. This triggers a `created` AgentSessionEvent webhook containing an `agentSession` object with the relevant issue, comment, and context" ([Getting Started](https://linear.app/developers/agents)). The payload type is `AgentSessionEventWebhookPayload` ([Developing the Agent Interaction](https://linear.app/developers/agent-interaction)), whose SDL fields are: `action: String!`, `agentSession: AgentSessionWebhookPayload!`, `agentActivity: AgentActivityWebhookPayload`, `appUserId: String!`, `oauthClientId: String!`, `organizationId: String!`, `guidance: [GuidanceRuleWebhookPayload!]`, `previousComments: [CommentChildWebhookPayload!]`, `promptContext: String`, `type: String!`, `webhookId: String!`, `webhookTimestamp: Float!` ([SDL](https://raw.githubusercontent.com/linear/linear/refs/heads/master/packages/sdk/src/schema.graphql)). Two actions only:

- `created` — "A new Agent Session has been created (triggered by a user mention or delegation). You should start a new agent loop in response." `promptContext` is "a formatted string containing the session's relevant context, such as issue details, comments, and guidance"; it is "Present only for `created` events" (SDL). Structured equivalents live in `agentSession.issue`, `agentSession.comment`, `previousComments`, `guidance`.
- `prompted` — "A user sent a new message into an existing Agent Session. This message is located in the `agentActivity.body` field of the webhook payload." ([Developing the Agent Interaction](https://linear.app/developers/agent-interaction))

`promptContext` is a pseudo-XML envelope; the documented example wraps `<issue identifier="ENG-123">` with title/description/team/labels/parent-issue/project, then `<primary-directive-thread comment-id="…">` with `<comment author=… created-at=…>` children, sibling `<other-thread>` blocks, and `<guidance><guidance-rule origin="team" team-name="Engineering">…</guidance-rule></guidance>` (ibid.). `guidance` is "any instructions configured at the workspace, parent team, or team level—such as preferred repositories or task constraints" (ibid.), and the SDL adds "The nearest team-specific guidance should take highest precedence."

`AgentSessionEvent` "webhooks only send events to your specific agent" (ibid.) — no filtering needed on Rocky's side beyond `appUserId`.

**Lifecycle.** "Agent sessions can have one of 6 states: `pending`, `active`, `error`, `awaitingInput`, `complete`, `stale`. These will be visible to users. You don't need to manage agent session state manually. Linear tracks session lifecycle automatically based on the last emitted activity" ([Developing the Agent Interaction](https://linear.app/developers/agent-interaction)). The SDL confirms `enum AgentSessionStatus { active awaitingInput complete error pending stale }` and exposes read-only timestamps `startedAt`, `endedAt`, `dismissedAt`, `dismissedBy`, plus `summary` ("A human-readable summary of the work performed in this session"). `AgentSessionUpdateInput` has **no status field** — the only agent-writable fields are `externalUrls`/`addedExternalUrls`/`removedExternalUrls`/`externalLink` and `plan`, each marked "Only updatable by the OAuth application that owns the session"; `dismissedAt` and `userState` are "[Internal] … Only updatable by internal clients" ([SDL](https://raw.githubusercontent.com/linear/linear/refs/heads/master/packages/sdk/src/schema.graphql)). Dismissal is a human action with a side effect Rocky must handle: "The time a user dismissed this agent session. When dismissed, **the agent is removed as delegate from the associated issue**" (SDL).

**The two deadlines — these are different numbers and both matter.**

1. Webhook HTTP response: "You must return a response from your webhook receiver within 5 seconds" ([Developing the Agent Interaction](https://linear.app/developers/agent-interaction)). This matches the generic webhook rule ("takes longer than 5 seconds (5000ms) to respond" counts as a failed delivery, [Webhooks](https://linear.app/developers/webhooks)).
2. Acknowledgement: "Emit a `thought` activity **within 10 seconds** to acknowledge the session has begun" ([Getting Started](https://linear.app/developers/agents)). Restated twice more: "If you receive a `created` event, you are expected to send an activity **or update your external URL** within 10 seconds to avoid the session being marked as unresponsive" ([Developing the Agent Interaction](https://linear.app/developers/agent-interaction)); and "The first response must be sent within 10 seconds of receiving the `created` event, or the agent will be shown as unresponsive" ([Interaction Best Practices](https://linear.app/developers/agent-best-practices)).

The escape hatch is worth noting for Rocky: setting `externalUrls` via `agentSessionUpdate` satisfies the 10 s requirement — "Doing so also prevents a new session from being marked unresponsive" ([Developing the Agent Interaction](https://linear.app/developers/agent-interaction)). So the daemon can point at Rocky's local UI *as* its acknowledgement.

**Stale window.** "Follow-up activities after the first response can still be sent for up to **30 minutes** before the session is considered stale. Note that this stale state is recoverable by sending another agent activity" ([Interaction Best Practices](https://linear.app/developers/agent-best-practices)). Practical consequence for a long Run: Rocky must emit *something* at least every 30 minutes, which is what `ephemeral` thoughts are for (§2). **Undocumented:** whether the 30-minute stale clock also runs while a session sits in `awaitingInput` waiting on a human. Nothing on the four agent pages addresses it. A spike must park a session in `awaitingInput` for >30 min and observe whether it flips to `stale`.

**Proactive sessions.** "If your agent was not delegated or mentioned but you would like to proactively create an agent session, you can do so via the SDK or API with the `agentSessionCreateOnIssue` or `agentSessionCreateOnComment` mutations" (ibid.). `AgentSessionCreateOnIssue` takes `issueId` (UUID *or* identifier like `LIN-123`) plus optional `externalUrls`; `AgentSessionCreateOnComment` takes `commentId` ([SDL](https://raw.githubusercontent.com/linear/linear/refs/heads/master/packages/sdk/src/schema.graphql)). Cyrus uses exactly this to start sessions it wasn't delegated ([`LinearActivitySink.createAgentSession`](https://github.com/ceedaragents/cyrus/blob/HEAD/packages/edge-worker/src/sinks/LinearActivitySink.ts)).

## 2. Activities: types, streaming, and rendering

**The one mutation.** `agentActivityCreate(input: AgentActivityCreateInput!)`. Input: `agentSessionId: String!`, `content: JSONObject!`, `ephemeral: Boolean`, `signal: AgentActivitySignal`, `signalMetadata: JSONObject`, `id: String` (client-supplied UUID v4) ([SDL](https://raw.githubusercontent.com/linear/linear/refs/heads/master/packages/sdk/src/schema.graphql)). Note `content` is deliberately loose — "This object is not strictly typed" — but "These are validated server-side, and invalid shapes will be rejected" ([Developing the Agent Interaction](https://linear.app/developers/agent-interaction)).

**Five emittable types, and their exact payloads** (verbatim from [Developing the Agent Interaction](https://linear.app/developers/agent-interaction); "Unless otherwise noted, all fields shown are required. Markdown is supported in `body` fields"):

| Type | Payload | Documented meaning |
|---|---|---|
| `thought` | `{type:"thought", body}` | "A thought or internal note." |
| `elicitation` | `{type:"elicitation", body}` | "Requests clarification or confirmation from the user." |
| `action` | `{type:"action", action, parameter, result?}` | "Describes a tool invocation. You may optionally include a result if the action has completed." |
| `response` | `{type:"response", body}` | "Indicates work has been completed or a final result is available." |
| `error` | `{type:"error", body}` | "Used to report an error or failure." |

A sixth type exists but is human-only: "you may see references to a `prompt` type `AgentActivity`. That is a user-generated message… **An agent cannot generate a `prompt` type activity**" (ibid.). The SDL's `AgentActivityCreatePromptInput` is marked "[Internal] Input for creating prompt-type agent activities (created by users)". `enum AgentActivityType { action elicitation error prompt response thought }`.

The `action` shape is a two-phase idiom, not a single event: the docs show `{action:"Searching", parameter:"San Francisco Weather"}` first and `{action:"Searched", parameter:"San Francisco Weather", result:"12°C, mostly clear"}` after — i.e. **the "completed" version is a new activity, not an update to the old one.** There is no `agentActivityUpdate` or `agentActivityDelete` in the SDL. Every progress step Rocky streams is append-only and permanent unless marked ephemeral.

**Ephemeral activities are the streaming mechanism.** "When creating an agent activity, you may optionally mark it as `ephemeral`. Ephemeral activities are displayed temporarily, and will be replaced when the next activity arrives from the agent… **Only `thought` or `action` type activities can be marked ephemeral**" (ibid.). The SDL field: "Whether the activity is ephemeral, and should disappear after the next agent activity." Cyrus's mapping is instructive as a working reference: standard tool calls are `ephemeral: true`, while `TodoWrite`/`Task` results are explicitly *not* ephemeral ([`AgentSessionManager.ts`](https://github.com/ceedaragents/cyrus/blob/HEAD/packages/edge-worker/src/AgentSessionManager.ts)).

**Rendering.** Markdown in `body` and in `action.result` ("// Markdown OK"). Two Linear-specific Markdown extensions are usable and relevant to Rocky's output:
- Mentions: "To include mentions in Agent Activity content, use plain Linear URLs in Markdown. These will be converted into mentions in the UI" ([Developing the Agent Interaction](https://linear.app/developers/agent-interaction)); a profile URL renders as `@user`, an issue URL as `@LIN-123 docs issue`.
- Collapsible sections: "use `+++ [some section title]` to start the section and `+++` to end it" ([GraphQL getting started](https://linear.app/developers/graphql?noRedirect=1#adding-collapsible-sections-in-markdown)) — the obvious container for long diffs/logs in a `response`.

**Terminal activities are mirrored into the comment thread.** "When work is complete, emit an `AgentActivity` with type `response`; or if you require additional actions from the user, emit an `AgentActivity` with type `elicitation` or `error`. **We will automatically create a comment under the comment thread as well**" ([Interaction Best Practices](https://linear.app/developers/agent-best-practices)). This is load-bearing for §4: whatever Markdown Rocky puts in a terminal activity also lands in a real Linear comment, and comments definitely render images.

**Reading history back — do not read comments.** "Comments may not be reliable to read from, as they are editable and may have changed since your agent's last run. Instead, rely on Agent Activities as these are frozen-in-time snapshots of user input. To reconstruct the full conversation, list the Agent Activities associated with the Agent Session" (ibid.), via `agentSession(id).activities` with an inline-fragment union spread, or the SDK's `activity.content.__typename` switch (SDK "53.0.0+", ibid.).

**Agent Plans** (technology preview): `agentSessionUpdate(id:, input: {plan: [...]})` where each step is `{content: string, status: "pending"|"inProgress"|"completed"|"canceled"}`. "**Note**: When updating a plan, agents must replace the existing plan in its entirety. They cannot update the status of just one item" ([Developing the Agent Interaction](https://linear.app/developers/agent-interaction)). Rocky must therefore hold the whole plan in memory and PUT-style replace it on every step transition.

**Undocumented rendering constraint found in Cyrus:** an activity with an empty or whitespace-only `body` is accepted by Linear and "rendered as an extra empty" bubble in the thread — Cyrus had to suppress them client-side ([`AgentSessionManager.empty-thought.test.ts`](https://github.com/ceedaragents/cyrus/blob/HEAD/packages/edge-worker/test/AgentSessionManager.empty-thought.test.ts)). Server-side validation does not catch this; Rocky must.

**Also available and undocumented:** `AgentActivity.pushSummary` (`AgentActivityPushSummary`: `baseSha`, `headSha`, `commitCount`, `commits[{sha,additions,deletions,changedFiles}]`) is marked "[Internal] … Only set on the activity for a successful push" in the SDL. Not writable by third-party agents as far as the SDL shows — this is how Linear's own coding agent reports diffs. Rocky cannot populate it.

## 3. Elicitation: the native "agent is asking the human something" state

**Yes, Linear has one, and it is a real session state.** `elicitation` "Requests clarification or confirmation from the user" and `awaitingInput` is one of the six session states Linear sets automatically "based on the last emitted activity" ([Developing the Agent Interaction](https://linear.app/developers/agent-interaction)). The human's answer comes back as a `prompt` activity, which "emit[s] a `prompted` webhook to you on creation" (ibid.) — so the round trip is fully event-driven, no polling.

**Does it block?** It blocks the *UI narrative*, not the agent. Linear surfaces `awaitingInput` to the user and stops treating the session as working, but:

- Nothing in the API prevents the agent from emitting further activities while in `awaitingInput`; state is derived from "the last emitted activity", so the next `thought` simply moves it back to `active`.
- The human can refuse to answer in the intended shape: "**Users aren't required to pick an option**—they can reply in free text, which dismisses the elicitation. Any selected option is emitted as a regular `prompt` activity. And since responses may include natural language, your agent should always involve an LLM when interpreting the prompt" ([Signals](https://linear.app/developers/agent-signals)).

So Linear's elicitation is a *soft* gate. If Rocky's Checkpoint must be a hard gate, the gate has to be enforced in Rocky's own run loop; Linear can only advertise it.

**The two documented signals, both of which map onto Checkpoint:**

`select` — "presents a list of options for the user to choose from as part of an elicitation activity. It's useful for confirmations, selecting a target (such as a GitHub repository), or any situation with multiple choices." Payload: `signal: "select"`, `signalMetadata: {options:[{label, value}, …]}`; "Each option may include both a `label` and a `value` and values can differ. GitHub repository URL options may render with enriched displayed content even if no `label` is provided" ([Signals](https://linear.app/developers/agent-signals)).

`auth` — "indicates that the agent requires the user to complete an account linking process before it can continue. When this signal is present, **Linear renders a temporary UI state containing a link for the user to complete the account linking flow. This UI is ephemeral and will be dismissed once a newer agent-initiated activity is received.** After the required action is completed, the agent should resume work by emitting a `thought` activity." Payload: `signal: "auth"`, `signalMetadata: {url, userId?, providerName?}`, where `userId` "restricts to a specific user" and non-targeted users see a "Waiting for [username] to link their account" variant (ibid.).

`auth` is nominally for account linking, but its mechanics — *a button in the session thread that opens an arbitrary HTTPS URL, scoped to one named user, auto-dismissed when the agent speaks again* — are exactly a "open the Checkpoint in Rocky" affordance. This is not a theoretical repurposing: Cyrus already ships `createApprovalElicitation(sessionId, body, approvalUrl)`, which emits `{type:"elicitation", body}` with `signal:"auth"` and `signalMetadata:{url: approvalUrl}` for generic approvals ([`AgentSessionManager.ts`](https://github.com/ceedaragents/cyrus/blob/HEAD/packages/edge-worker/src/AgentSessionManager.ts)). Cyrus likewise maps Claude Code's `AskUserQuestion` tool onto "Linear's select signal elicitation" (ibid., inline comments).

**Third signal in the enum, absent from the docs:** the SDL declares `enum AgentActivitySignal { auth continue select stop }`. `stop` and `auth`/`select` are documented; **`continue` is documented nowhere** on the Signals page. Cyrus maps it (`AgentActivitySignal.Continue`, [`LinearActivitySink.ts`](https://github.com/ceedaragents/cyrus/blob/HEAD/packages/edge-worker/src/sinks/LinearActivitySink.ts)) but its rendering and direction are unknown. A spike should emit `continue` on each activity type and observe.

**The human's stop path.** "The `stop` signal instructs the agent to halt work immediately. From the moment this signal is received, the agent must not perform any further actions—such as making code changes, updates, or additional API calls. After disengaging, the agent should emit a final activity—either of type `response` or `error`—to confirm that it has stopped" ([Signals](https://linear.app/developers/agent-signals)). It arrives as a `prompt` activity with `signal: "stop"` via the `prompted` webhook. Rocky must implement cancellation for this; it is a requirement of the Agent Interaction Guidelines ("An agent should respect requests to disengage", [AIG](https://linear.app/developers/aig)), not an optional nicety.

**Where Checkpoint should live, on the evidence.** Linear can carry: the question text (Markdown), a bounded option list (`select`), a per-user button into Rocky (`auth` + `url`), the visible `awaitingInput` state, and a free-text reply channel (`prompt` webhook). Linear cannot carry: multi-field forms, a diff viewer, images inline in the elicitation (§4), or a hard block. Split accordingly — the *decision* in Linear, the *artefact* in Rocky's UI behind the `auth`-signal button.

## 4. Attachments and images

**There is no image activity type.** `union AgentActivityContent = AgentActivityActionContent | AgentActivityElicitationContent | AgentActivityErrorContent | AgentActivityPromptContent | AgentActivityResponseContent | AgentActivityThoughtContent` ([SDL](https://raw.githubusercontent.com/linear/linear/refs/heads/master/packages/sdk/src/schema.graphql)). The agent pages never mention images or attachments in activities. The only vector is Markdown inside a `body`/`result` field.

**The upload flow is two steps and server-only.** `fileUpload(contentType: String!, filename: String!, size: Int!, makePublic: Boolean, metaData: JSON): UploadPayload!` returns `uploadFile { uploadUrl, assetUrl, contentType, filename, size, headers[{key,value}] }` (SDL). Then: "use the `fileUpload` mutation to request a pre-signed upload URL, then send a PUT request to that URL with the file content. You may request the signed upload URL from the client, but **the PUT request must be executed on the server**… Attempting to upload a file from the client-side will be blocked by Linear's Content Security Policy (CSP)" ([How to upload a file](https://linear.app/developers/how-to-upload-a-file-to-linear)). The PUT must carry `Content-Type`, `Cache-Control: public, max-age=31536000`, and every header from the `headers` array. The returned `assetUrl` "can be used in API mutations, like creating an issue or a comment" (ibid.).

Cyrus's `linear_upload_file` MCP tool is a working reference implementation of exactly this, including the `Cache-Control` value and the `makePublic` pass-through ([`packages/mcp-tools/src/tools/cyrus-tools/index.ts`](https://github.com/ceedaragents/cyrus/blob/HEAD/packages/mcp-tools/src/tools/cyrus-tools/index.ts)). Its stated purpose is Rocky's exact use case: Cyrus hooks `playwright_screenshot` and `mcp__chrome-devtools__take_screenshot` to nudge the model into calling `linear_upload_file` "so screenshots… [are] viewable in Linear **comments**" ([`EdgeWorker.screenshot-upload-hooks.test.ts`](https://github.com/ceedaragents/cyrus/blob/HEAD/packages/edge-worker/test/EdgeWorker.screenshot-upload-hooks.test.ts)) — note: comments, not activities. That is the strongest available signal that the activity stream is *not* the place images render.

**Reading assets back is authenticated.** "Files on `uploads.linear.app` are not public… You must authenticate to access these files", using "the same access token and `authorization` header as you would when making requests to our GraphQL API"; alternatively request signed URLs via a `public-file-urls-expire-in` header (seconds) ([File storage authentication](https://linear.app/developers/file-storage-authentication)). Restated: "Linear hosts images and other assets uploaded into Linear behind authentication… all images will require authentication to be displayed outside Linear's application… If you're displaying images outside Linear's applications, you should download and self-host them" ([GraphQL getting started](https://linear.app/developers/graphql?noRedirect=1#accessing-images)). Consequence for Rocky's own web UI: it cannot hotlink a Linear `assetUrl` into an `<img>` tag; it must proxy with the app token or mint a signed URL. Inbound direction is symmetrical — Cyrus downloads issue attachments with `Authorization: Bearer ${linearToken}` before handing local paths to the model ([`AttachmentService.ts`](https://github.com/ceedaragents/cyrus/blob/HEAD/packages/edge-worker/src/AttachmentService.ts)).

**Issue attachments are link cards, not images.** `attachmentCreate` requires `issueId`, `title`, `url` ("Attachment location which is also used as an unique identifier for the attachment. If another attachment is created with the same `url` value, existing record is updated instead"), and accepts `subtitle`, `metadata`, `groupBySource`, `commentBody` ("Create a linked comment with markdown body"), and `iconUrl` — "**An icon url to display with the attachment. Should be of jpg or png format. Maximum of 1MB in size. Dimensions should be 20x20px for optimal display quality**" ([SDL](https://raw.githubusercontent.com/linear/linear/refs/heads/master/packages/sdk/src/schema.graphql); see also [Attachments](https://linear.app/developers/attachments)). So a UI-inspector screenshot cannot be "posted as an attachment" in any visually useful sense — the attachment can only *link* to it with a 20x20 favicon. Attachment `metadata` does support richer modal content (`title`, `messages[{subject,body,timestamp}]`, `attributes[{name,value}]`) per the Attachments page, but that is text, not imagery.

**Size limits: undocumented.** `fileUpload` takes an explicit `size: Int!`, and neither the upload guide, the attachments page, nor the API docs state a maximum. The only file-size number in Linear's docs is unrelated (25 MB for email-created issues). A spike must probe the real cap and the failure mode (does `fileUpload` reject, or does the presigned PUT 400?).

**Net for the UI-inspector design.** Confirmed possible: upload a PNG server-side, embed it as `![](assetUrl)` in a `response` body, and rely on the auto-mirrored comment (§2) to render it. Confirmed impossible: an image-typed activity; a screenshot displayed as an issue attachment; hotlinking an `assetUrl` from Rocky's UI without auth. Undocumented and must be spiked: whether the image renders inside the agent-session activity stream itself, and the max upload size.

## 5. Issue state transitions and discovering workflow states

**The agent's token can move issue state — Linear instructs it to.** "If your agent is delegated by a human to work on an issue that is not in a `started`, `completed`, or `canceled` status type, move the issue to the first status in `started` when your agent begins work. You can fetch this by querying the team's workflow states filtered by `type: { eq: "started" }`, and selecting the one with the lowest `position`" ([Interaction Best Practices](https://linear.app/developers/agent-best-practices)), with the query given verbatim:

```graphql
query TeamStartedStatuses($teamId: String!) {
  team(id: $teamId) { states(filter: { type: { eq: "started" } }) { nodes { id name position } } }
}
```

**How to discover a team's states for config mapping.** `WorkflowState` carries `id`, `name` ("e.g. 'In Progress', 'Done', 'Backlog'"), `color`, `description`, `position` ("States are displayed in ascending order of position within their type group"), `team`, `inheritedFrom`, and `type` — "One of `\"triage\"`, `\"backlog\"`, `\"unstarted\"`, `\"started\"`, `\"completed\"`, `\"canceled\"`, `\"duplicate\"`" ([SDL](https://raw.githubusercontent.com/linear/linear/refs/heads/master/packages/sdk/src/schema.graphql)). Note `type` is a `String!`, not an enum — Rocky's config validation cannot lean on GraphQL enum checking. Either `team(id).states(filter:)` or the top-level `workflowStates` connection works. Mapping config should key on `type` + `position`, not on `name`, since names are workspace-authored.

**Delegate self-assignment.** "If your agent is working on implementation and no `Issue.delegate` is currently set, it should set itself as the delegate to make the agent's role in the issue more explicit" (Best Practices); `IssueUpdateInput.delegateId` — "The identifier of the agent user to delegate the issue to" (SDL). The agent's own app-user id comes from `query Me { viewer { id } }` ([Getting Started](https://linear.app/developers/agents)).

**Two behavioural rules Rocky must encode, not just capabilities:**
- "If an automation has delegated to an agent, keep it in triage state and leave assignment up to a human actor to action" (Best Practices) — i.e. automation-originated sessions must *not* trigger a state move. The discriminator is `agentSession.creator`, which is "Null if the session was initiated via automation or by an agent user, with no responsible human user" (SDL).
- Writes are subject to a quiet audit-log quirk: "Changes made to an issue's properties in the first 3 minutes are considered part of the issue creation process, and won't be added to the activity log as changes to the issue" ([GraphQL getting started](https://linear.app/developers/graphql?noRedirect=1)).

**Scope required.** State changes need `write` (or, narrowly, nothing narrower exists — `issues:create` only "Allows creating new issues and their attachments") ([OAuth 2.0](https://linear.app/developers/oauth-2-0-authentication)). Team access is a separate axis: "The team access available to your app can be changed or revoked at any time by workspace admins", signalled by the `PermissionChange` webhook with `action: "teamAccessChanged"` carrying `canAccessAllPublicTeams`, `addedTeamIds`, `removedTeamIds` ([Getting Started](https://linear.app/developers/agents), [Interaction Best Practices](https://linear.app/developers/agent-best-practices)).

## 6. OAuth app creation: what each developer must actually do

**One app per developer is the intended shape, and the manifest flow is how you make it reproducible.** Apps are created at [`linear.app/settings/api/applications/new`](https://linear.app/developers/oauth-2-0-authentication). Rather than hand-filling the form, "OAuth app manifests let developers define a Linear OAuth app as structured data instead of filling the form manually", passed "to the create page through a single `manifest` query parameter", and explicitly aimed at Rocky's situation: "useful for hosted platforms that want a reproducible setup flow, and for **self-hosted or open-source projects that want to link to a pre-populated app configuration**" ([OAuth application manifests](https://linear.app/developers/oauth-app-manifests)).

The authoritative field list is the published JSON Schema, [`https://linear.app/.well-known/oauth-app-manifest.schema.json`](https://linear.app/.well-known/oauth-app-manifest.schema.json) (fetched 2026-08-28): required top-level `schemaVersion` (const `"1.0.0"`), `developer.name` (2–80 chars), `oauth`; optional `distribution` (`private` | `public`, default `private`), `display.description` (max 1000), `display.iconUrl` ("Use an image at least 256x256px"), `webhook`. Under `oauth`: required `client_name` (2–80) and `redirect_uris` (1–32, unique, http(s)); optional `client_uri` ("Required for public applications" — enforced by an `allOf`/`if` clause) and `grant_types` (must contain `authorization_code`; the only other value is `client_credentials`). Under `webhook`: required `url` (HTTPS only — the pattern is `^[Hh][Tt][Tt][Pp][Ss]://`, max 1000 chars) and `resourceTypes` (1–22 from a fixed enum including `AgentSessionEvent`, `AppUserNotification`, `PermissionChange`); `enabled` defaults true.

Two naming constraints that will bite a per-developer naming scheme, both enforced by regex in the schema: `client_name` "must not contain \"Linear\"" (case-insensitive) and "must not contain http:// or https://". Cyrus's setup skill hit this and warns about it in prose: "If `<AGENT_NAME>` contains the word 'Linear' or a URL, choose a different OAuth application name before building the manifest. Linear rejects OAuth client names with those values" ([`skills/cyrus-setup-linear/SKILL.md`](https://github.com/ceedaragents/cyrus/blob/HEAD/skills/cyrus-setup-linear/SKILL.md)). `"Rocky (Jan Jaap)"` is fine.

**Scopes are NOT in the manifest.** The manifest covers display/OAuth/webhook config only; there is no `scopes` property. Scopes are requested at authorize time in the `scope` query parameter ([OAuth 2.0](https://linear.app/developers/oauth-2-0-authentication)).

**`actor=app` is mandatory, and it costs an admin.** "To install your agent into a Linear workspace in the OAuth authorization url add the `actor=app` parameter to switch to an app installation rather than requesting authentication as the installing user. Because this will be installed with a workspace scope **admin permissions are required to complete the installation**" ([Getting Started](https://linear.app/developers/agents)). Contrast `actor=user`, where "actions performed with the OAuth token will appear to come from that user" ([OAuth actor authorization](https://linear.app/developers/oauth-actor-authorization)). `actor=application` is the deprecated predecessor; `actor=app` "supersedes any references to `actor=application` and can be used for all agent, app, and service account use-cases" (Getting Started).

Hard constraint on `actor=app`: "**integrations using the `actor=app` mode are not able to also request `admin` scope**" (ibid.). Since "Only workspace admins, or OAuth applications with the `admin` scope, can create or read webhooks" ([Webhooks](https://linear.app/developers/webhooks)), a Rocky agent app can *never* manage data-change webhook records itself. It gets its webhooks only via the OAuth-app mechanism (§7).

**Scopes Rocky needs:**

| Scope | Documented effect |
|---|---|
| `read` | "(Default) Read access for the user's account. This scope will always be present." |
| `write` | "Write access for the user's account" — needed for state moves, delegate, comments, uploads |
| `app:assignable` | "Allow the app to be assigned as a delegate on issues and made a member of projects" |
| `app:mentionable` | "Allow the app to be mentioned in issues, documents, and other editor surfaces" |
| `customer:read` / `customer:write`, `initiative:read` / `initiative:write` | optional, per-entity-family gates |

Sources: [Getting Started](https://linear.app/developers/agents), [OAuth 2.0](https://linear.app/developers/oauth-2-0-authentication). Without `app:assignable` the app is *not delegatable* — this is opt-in, "the ability to mention and assign your agent is optional and must be requested" (Getting Started). Note `app:assignable` also implies project membership, which is broader than Rocky needs; there is no narrower scope.

**Does each app appear as its own agent user? Yes.** "Agents behave similar to other users in a workspace"; "the name and icon of your application will be how the agent appears in workspaces where it is installed (e.g. in the mention and filter menus), so it is best to choose something short, recognizable, but unique" (Getting Started). Per-workspace identity: "Your app will have a **unique ID for each workspace** it is installed within", fetched with `query Me { viewer { id } }`; "We highly recommend storing this ID alongside your access token" (ibid.). The SDL corroborates: `AgentSession.appUser: User!` — "The agent user that is associated with this agent session." Users delegate by assignment: "Delegate issues to them by assigning the issue to the agent" ([AI Agents docs](https://linear.app/docs/agents-in-linear)).

**Cost per developer, itemised.**
1. Someone creates the app in a workspace. Manifest URL makes this ~one click plus review, but the secrets must be copied by hand — there is no API to read a client secret back, and Cyrus's skill deliberately routes them through the user (ibid.).
2. A **workspace admin** must complete the `actor=app` install. If the workspace has `Organization.oauthAppReview` enabled ("Whether the workspace has opted for having to approve all OAuth applications for install", [SDL](https://raw.githubusercontent.com/linear/linear/refs/heads/master/packages/sdk/src/schema.graphql)), the install additionally raises an `OauthClientApproval` record — "When a user attempts to install an OAuth application that requires admin approval, an approval record is created. A workspace admin can then approve or deny the request" — and re-approval is needed for later scope additions: "Additional OAuth scopes requested after the initial approval. These scopes are not yet approved and require a separate admin decision" (SDL). Admins are notified via `OauthClientApprovalNotification`.
3. An admin chooses team access: admins "must choose which teams the agent has access to" during setup ([AI Agents docs](https://linear.app/docs/agents-in-linear)).
4. Token upkeep: authorization-code access tokens are "valid for 24 hours" with rotating refresh tokens and "a 30-minute grace period" for replaying a failed refresh; "All OAuth2 applications were migrated to the new refresh token system on April 1, 2026" ([OAuth 2.0](https://linear.app/developers/oauth-2-0-authentication)).

**Two costs that are easy to miss.** First, privacy/blast radius: Linear itself warns "It is **highly recommended** you create a workspace for the purpose of managing the OAuth2 Application, as **each admin user will have access**" (ibid.). N per-developer apps in the company workspace means every workspace admin can see and edit every developer's Rocky app, including rotating its secrets. Second, `client_credentials` may collapse steps 1–2 for a self-hosted single-workspace case: "The token generated using this grant type will be an `app` actor token that has access to all public teams in the workspace and is valid for 30 days", no refresh token, up to "1000 active client credentials tokens in parallel, provided each token uses the same scopes", and "we will also invalidate your app's client credentials tokens if its client secret is rotated" (ibid.). **Undocumented:** whether `app:assignable`/`app:mentionable` can be granted through `client_credentials`, i.e. whether a client-credentials-only app becomes a delegatable agent user without any authorize redirect. That is a cheap, high-value spike — it would remove the OAuth dance from per-developer setup entirely.

**How many apps per workspace?** **Undocumented.** No limit appears in the OAuth docs, the agents docs, or the manifest schema. Two data points that make many apps plausible: "It does not cost anything to develop agents in Linear" and "agents installed in your workspace **do not count as billable users**" ([Getting Started](https://linear.app/developers/agents)), restated as "Agents are not counted as billable seats in Linear" ([AI Agents docs](https://linear.app/docs/agents-in-linear)). Treat as unbounded-but-unverified; a spike should create ~5 apps in one workspace.

## 7. Webhook registration, signature verification, retries

**Registration is a property of the OAuth client, not of a webhook record.** "OAuth applications can configure webhook settings. Once those settings are configured, **each time a new organization authorizes the given application, a webhook will be created for that organization that posts to the provided webhook URL**" ([Webhooks](https://linear.app/developers/webhooks)). The SDL makes the indirection explicit on `Webhook.url`: "The destination URL where webhook payloads will be sent via HTTP POST. **Null for OAuth application webhooks, which use the webhook URL configured on the OAuth client instead**" ([SDL](https://raw.githubusercontent.com/linear/linear/refs/heads/master/packages/sdk/src/schema.graphql)). `OAuthApplication` correspondingly has `webhookUrl`, `webhookEnabled`, `webhookResourceTypes`.

Good news: one URL change re-points every workspace at once — Rocky never has to iterate per-workspace webhook records. Bad news: `webhookUpdate(input: WebhookUpdateInput{url,…})` is the wrong lever (it edits data-change webhooks, and needs admin, which `actor=app` cannot have), so the question reduces to: can the *OAuth client's* `webhookUrl` be changed programmatically?

**Answer: only via ALPHA, undocumented mutations, and only for apps created by another app.** The public docs describe no way to change it — the OAuth page and the manifest page both treat webhook URL as set-at-create in the settings UI. But the SDL exposes:

- `oauthApplicationCreate(input: OAuthApplicationCreateInput!)` — "**[ALPHA]** Creates an OAuth application **owned by the calling OAuth application**." Input includes `name`, `developer`, `redirectUris`, `webhookUrl`, `webhookResourceTypes`, `grantTypes`, `imageUrl`, `description`, and an `idempotencyKey` ("Reusing the same key with the same managing OAuth application returns the existing OAuth application instead of creating a duplicate"). The payload returns `clientSecret` ("Store this value securely because it cannot be retrieved later") and `webhookSecret`.
- `oauthApplicationUpdate(id, input: OAuthApplicationUpdateInput!)` — "**[ALPHA]** Updates an OAuth application **created by the calling OAuth application**." Input includes `webhookUrl`, `webhookEnabled`, `webhookResourceTypes`, `redirectUris`, `name`, `imageUrl`.
- `oauthApplicationRotateSecret`, `oauthApplicationRotateWebhookSecret`, `oauthApplicationArchive`, plus queries `oauthApplication(id)` and `oauthApplications` — "[ALPHA] OAuth applications created by the calling OAuth application through the public API."

(All from the [SDL](https://raw.githubusercontent.com/linear/linear/refs/heads/master/packages/sdk/src/schema.graphql); none of these appear on any `linear.app/developers` page.)

So there are exactly two architectures for Rocky's ephemeral tunnel:

- **(A) Stable hostname.** Accept that the webhook URL is fixed at app creation and give the daemon a durable public URL — a named Cloudflare tunnel or reserved ngrok domain. This is what Cyrus does: its setup skill bakes `${CYRUS_BASE_URL}/linear-webhook` into the manifest and requires `CYRUS_BASE_URL` to have been established by a separate endpoint-setup step ([`SKILL.md`](https://github.com/ceedaragents/cyrus/blob/HEAD/skills/cyrus-setup-linear/SKILL.md)); the repo ships a `cloudflare-tunnel-client` package and `docs/CLOUDFLARE_TUNNEL.md` for precisely this. Note the manifest schema forces HTTPS, so plain-HTTP localhost is out even in dev.
- **(B) Managing app.** digimondo publishes one "Rocky Bootstrap" OAuth app; each developer authorizes it once; the daemon then calls `oauthApplicationCreate` (idempotency-keyed per developer) to mint "Rocky (Jan Jaap)" and `oauthApplicationUpdate` on every boot to re-point `webhookUrl` at the fresh tunnel. This is the only path that makes an ephemeral tunnel work. It rests entirely on ALPHA, undocumented mutations; a spike must establish (i) whether they work with a normal app token and what scope they need, (ii) whether a child app can still be installed with `actor=app` and appear as a delegatable agent user, (iii) whether the child install still needs admin approval, and (iv) whether `webhookUrl` changes take effect immediately for already-authorized workspaces.

**Subscribing to the right categories.** "In the configuration, enable webhooks and make sure to select **Agent session events** at the bottom. Enabling this category will notify your webhook when events occur that are directly relevant to your app's user"; "If you're just getting started, selecting Inbox notifications and Permission changes may also be helpful" ([Getting Started](https://linear.app/developers/agents)). The `WebhookResourceType` enum (SDL) lists `AgentSessionEvent`, `AppUserNotification`, `PermissionChange`, `OAuthAuthorization`, plus the data-change types. **A visible side effect worth flagging to design:** "Once you subscribe to `AgentSessionEvent` webhooks, **customers will begin seeing Agent Session UI in Linear. This happens as soon as the event category is enabled, even if you're only listening for debugging purposes**" ([Developing the Agent Interaction](https://linear.app/developers/agent-interaction)). There is no dark-launch mode.

Two adjacent categories Rocky will want: `AppUserNotification` ("triggered when something directly involves your app user—like when an agent is unassigned from an issue or a user reacts to a comment from the agent"), with useful actions `issueMention`, `issueEmojiReaction`, `issueCommentMention`, `issueCommentReaction`, `issueAssignedToYou`, `issueUnassignedFromYou`, `issueNewComment`, `issueStatusChanged`; and `PermissionChange`/`teamAccessChanged` (§5). Revocation arrives as `{type:"OAuthApp", action:"revoked", …}` ([Interaction Best Practices](https://linear.app/developers/agent-best-practices)).

**Signature verification.** "Linear-Signature HTTP header with every webhook request. This header contains a hex-encoded HMAC-SHA256 signature of the raw body contents, signed using the webhook's signing secret… It's strongly recommended to use raw request body rather than restringifying a parsed JSON body, otherwise the signature may differ", compared with `crypto.timingSafeEqual` ([Webhooks](https://linear.app/developers/webhooks)). The `User-Agent` is `Linear-Webhook`. Replay protection: "check to ensure that the webhook timestamp is reasonably current before processing the request", the documented threshold being `Math.abs(Date.now() - req.body.webhookTimestamp) > 60 * 1000` (ibid.). The signing secret is per-app (`oauthApplicationRotateWebhookSecret` rotates it, SDL).

**Source-IP allowlist.** "Linear sends webhooks from the following IP addresses: 35.231.147.226, 35.243.134.228, 35.196.141.51, 34.140.253.14, 34.38.87.206, 34.62.119.29, 34.134.222.122, 35.222.25.142, 34.60.255.158. We may occasionally update this list to add new IP addresses" (ibid.). Cyrus hardcodes exactly this list ([`WebhookIpValidator.ts`](https://github.com/ceedaragents/cyrus/blob/HEAD/packages/core/src/security/WebhookIpValidator.ts)) — note the doc's own caveat makes a hardcoded list a maintenance liability, and it is unusable behind a tunnel that rewrites the source IP.

**Delivery and retries.** Endpoint requirements: "available in a publicly accessible HTTPS, non-localhost URL" and respond HTTP 200. "If a delivery fails (i.e. server unavailable, takes longer than **5 seconds (5000ms)** to respond, or responds with a non-200 HTTP status code), the push will be retried a maximum of **3 times**. A backoff delay is used: the attempt will be retried after **1 minute, 1 hour, and finally after 6 hours**. If the webhook URL continues to be unresponsive the webhook **might be disabled by Linear, and must be re-enabled again manually**" (ibid.).

That retry schedule is fatal for a laptop daemon: a `created` event missed while Rocky is down retries at +1 min, then not again until +1 h. **The 10-second acknowledgement deadline is measured from the event Rocky actually receives**, so a retry at +1 h that Rocky answers within 10 s is presumably fine — but the user has stared at an unresponsive agent for an hour. Rocky should therefore reconcile on boot rather than trusting webhook delivery, and the SDL constrains how: the root `agentSessions` connection ("All agent sessions.") accepts **only pagination and `orderBy`** — no `filter` argument, so it cannot be narrowed to this app user or to `awaitingInput` sessions; `Issue.agentSessions` and `Comment.agentSessions` are both marked "[Internal]". `Issue` has no singular `agentSession` field at all. The usable paths are `viewer { delegatedIssues { … } }` ("Issues delegated to this user.", public) or `issues(filter: { delegate: { id: { eq: $appUserId } } })` (`IssueFilter.delegate: NullableUserFilter`, public), plus `agentSession(id)` for session ids Rocky has persisted itself. **Practical upshot: Rocky must durably persist `agentSessionId` per Run at `created` time, because there is no public query that maps an issue back to its agent sessions.** Failures are introspectable: `Webhook.failures` returns "[INTERNAL] Webhook failure events associated with the webhook (last 50)" with `httpStatus`, `responseOrError` ("Truncated to 1000 characters") and a retry-stable `executionId` (SDL) — though reading webhooks needs admin, which `actor=app` cannot have.

## 8. Rate limits relevant to streaming a long Run

All from [Rate limiting](https://linear.app/developers/rate-limiting). Leaky bucket, "tokens are refilled with a constant rate of `LIMIT_AMOUNT / LIMIT_PERIOD`".

| Auth | Requests/h | Complexity/h | Scoped per |
|---|---|---|---|
| OAuth App | **5,000** | **2,000,000** | **User (or App User)** |
| API key | 2,500 | 3,000,000 | User |
| Unauthenticated | 600 | 100,000 | IP address |

So the limit that governs Rocky is **per app user, i.e. per (app, workspace) pair** — each developer's own "Rocky (Jan Jaap)" app gets its own 5,000/h bucket. That is a genuine argument *for* per-developer apps: N developers on one shared app would share one bucket.

Budget sanity check: 5,000 requests/hour is ~1.4/s sustained. An `agentActivityCreate` is a small mutation, so complexity is not the binding constraint — request count is. A Run that emits a start-action and a completed-action per tool call spends 2 requests per tool call; ~2,400 tool calls per hour is the ceiling. Verbose per-token streaming is not affordable; batching into ephemeral thoughts is.

Also relevant:
- "Maximum complexity of a single query at any time to **10,000 points**. Your query will always get rejected if it exceeds that." Complexity model: "Each property is 0.1 point, each object is 1 point and any connection multiplies its children's points based on the given pagination argument, **or the default 50**." Reconstructing a long session's activities must paginate with explicit `first:`.
- Per-endpoint limits exist and are not published: "Some queries and mutations have individual request rate limits that are lower than the global request limit… The window for each endpoint can be different, and is described in the response body", surfaced via `X-RateLimit-Endpoint-{Requests-Limit,Requests-Remaining,Requests-Reset,Name}`. **Whether `agentActivityCreate` or `fileUpload` carry such a limit is undocumented** — Rocky should log `X-RateLimit-Endpoint-Name` and treat it as discoverable at runtime.
- Headroom scales with the customer: "We dynamically increase rate limits for workspace level OAuth apps using Actor Authorization based on number of paid users in that workspace."
- Rate-limit errors come back as **HTTP 400** with a GraphQL `errors` entry, not 429 — error handling must inspect the body.
- Standing advice: "One thing that we especially discourage is polling the API to fetch updates." Rocky's boot-time reconciliation (§7) should be a bounded query, not a poll loop.

## 9. Impossible, and undocumented-with-a-spike

**Impossible (do not design around, do not emulate):**
- An image, file, or attachment as an agent activity — the content union has six members, all text ([SDL](https://raw.githubusercontent.com/linear/linear/refs/heads/master/packages/sdk/src/schema.graphql)).
- A screenshot rendered as an issue attachment — attachments are link cards with a 20x20px, max-1MB icon (SDL).
- Editing or deleting an emitted activity — no mutation exists. Correction means appending; the only erasure is `ephemeral`, and only for `thought`/`action`.
- Setting session status directly — `AgentSessionUpdateInput` has no status field; "Linear tracks session lifecycle automatically" ([Developing the Agent Interaction](https://linear.app/developers/agent-interaction)).
- Emitting a `prompt` activity, i.e. simulating a human reply — "An agent cannot generate a `prompt` type activity" (ibid.).
- A hard block on the human — an elicitation can be dismissed with free text ([Signals](https://linear.app/developers/agent-signals)).
- `actor=app` + `admin` scope together, and therefore any agent-token management of data-change webhooks ([Getting Started](https://linear.app/developers/agents); [Webhooks](https://linear.app/developers/webhooks)).
- Hotlinking a Linear `assetUrl` into Rocky's web UI — assets are behind auth; "you should download and self-host them in your application's environment" ([GraphQL getting started](https://linear.app/developers/graphql?noRedirect=1#accessing-images)).
- A dark launch of agent-session support — enabling `AgentSessionEvent` immediately shows Agent Session UI to users ([Developing the Agent Interaction](https://linear.app/developers/agent-interaction)).
- Populating `AgentActivityPushSummary` (commit/diff stats on an activity) — "[Internal]" in the SDL.

**Undocumented — a spike must answer these, and Rocky must not assume either way:**
1. Does an image embedded as `![](assetUrl)` render **inside the activity stream**, or only in the mirrored comment? (Cyrus's screenshot hooks only ever claim "viewable in Linear comments".) This decides whether the UI-inspector output lives in Linear at all.
2. Maximum `fileUpload` size, and whether over-size fails at `fileUpload` or at the presigned `PUT`.
3. Does the 30-minute stale clock run while a session is in `awaitingInput`? If it does, a Checkpoint left overnight goes stale and Rocky needs a keep-alive.
4. What does the `continue` signal do, on which activity types, and in which direction?
5. Do the `[ALPHA]` `oauthApplicationCreate` / `oauthApplicationUpdate` mutations work with an ordinary app token; what scope do they need; does a child app install with `actor=app` as a delegatable agent user; does it still need admin approval; and does a `webhookUrl` change take effect immediately for already-authorized workspaces?
6. Can `client_credentials` grant `app:assignable`/`app:mentionable`, i.e. can a per-developer app become a delegatable agent without an authorize redirect?
7. Is there a per-endpoint rate limit on `agentActivityCreate` / `fileUpload`? (Read `X-RateLimit-Endpoint-Name` under load.)
8. How many OAuth apps does one workspace tolerate?
9. Is there a length cap on activity `body` / `action.result`, and does over-long content truncate or reject?
10. Behaviour when the same session receives a `prompted` event while the agent is mid-turn — the SDL hints at internal queueing (`AgentActivity.queued`: "[Internal] Whether this activity is queued for later processing. Queued activities are not sent to the agent until the session reaches a terminal state") but this is not exposed or documented for third-party agents.

## 10. Map assumptions to revisit

1. **Checkpoint can be substantially native.** Linear supplies `awaitingInput` + `elicitation` + `select` options + an `auth`-signal button into an arbitrary Rocky URL. Design the Checkpoint as: question and bounded choices in Linear; the artefact (diff, screenshots, form) behind the button in Rocky's local UI. Do not build a Linear-side emulation of blocking — Linear's gate is advisory; enforce in Rocky's run loop.
2. **UI-inspector screenshots may not be visible where the map assumes.** There is no image activity. Plan for the mirrored-comment route (`response` with `![](assetUrl)`) and a Rocky-hosted gallery reached via `externalUrls`, and treat in-activity image rendering as unproven until spike #1.
3. **The ephemeral-tunnel assumption is the biggest casualty.** The webhook URL is fixed on the OAuth client at creation, changeable only in the settings UI or through ALPHA app-management mutations that require a managing app. Either commit to a stable hostname per developer (Cyrus's answer) or take on the ALPHA dependency knowingly.
4. **Per-developer apps are correct for a reason the map may not have recorded:** the 5,000 req/h limit is per app user, so per-developer apps multiply headroom rather than sharing it. But the setup is not self-service — every app needs a workspace admin to complete `actor=app` install, possibly an approval record, and a manual secret copy; and every workspace admin can see and edit every other developer's app.
5. **Webhook retry backoff (1 min / 1 h / 6 h, then possible disablement) makes webhook-only delivery unsafe for a laptop daemon.** Boot-time reconciliation against `agentSessions` is not optional.
6. **Two deadlines, not one:** 5 s to return HTTP 200, 10 s to emit the first activity — and the 10 s can be satisfied by an `agentSessionUpdate` external-URL write instead of a thought, which is useful when Rocky needs to warm up.
7. **Everything above is a Developer Preview** ([Getting Started](https://linear.app/developers/agents)), with Agent Plans in technology preview and app management in ALPHA. Pin `@linear/sdk` (activity-content type narrowing needs 53.0.0+ per [Interaction Best Practices](https://linear.app/developers/agent-best-practices)) and expect churn.
