# SCM Integration Surfaces: GitHub vs GitLab Feasibility Matrix

Date: 2026-08-24
Sources: official docs only (docs.github.com, docs.gitlab.com).

**TL;DR** — GitHub gives us everything in one primitive: a GitHub App (install-per-repo flow, distinct bot identity, short-lived scoped tokens, centralized webhooks, and exclusive write access to the Checks API for the "Vercel-style" check with markdown summary + inline annotations). GitLab has no app/install primitive: "add a repo" means an OAuth grant plus programmatically creating a project webhook (needs Maintainer+), and a distinct bot identity requires a project/group access token (paid on GitLab.com) or a service account. GitLab's check surface is the commit-status API (shows as an `external` pipeline job — no markdown tab, no annotations); the richer "external status checks" feature is Ultimate-only. Two webhook wins for GitLab: it emits emoji-reaction events (GA in 17.5) where GitHub has no reactions webhook at all (polling required), and its MR `update` hook carries `oldrev` for push detection. Inline commenting is feasible on both, but GitLab's position object (3 SHAs + old/new path/line) is far more brittle than GitHub's `line`/`side`. Batched reviews exist on both (GitHub review with comments array; GitLab draft notes + `bulk_publish`). OAuth sign-in works on both; self-managed GitLab forces per-instance app registration.

## Feasibility matrix

| Capability | GitHub | GitLab | Divergence |
|---|---|---|---|
| App/install primitive | GitHub App: user picks "All / Only select repositories" at install | None. OAuth grant is all-or-nothing per user; webhook must be created per project via API (Maintainer+) | **High** |
| Distinct bot identity/avatar | Automatic (`app[bot]`, own avatar) | Only via project/group access-token bot user (Premium+ on GitLab.com), or a service account; user-OAuth token posts as the user | **High** |
| Server-side token | Installation token, ~1 h, scoped to repos+permissions | OAuth token 2 h + refresh; or access token (365-day default, rotate API) | Medium |
| Webhook on MR/PR open & new commits | `pull_request` `opened`/`synchronize` (with `before`/`after`) | MR event `open`/`update` with `object_attributes.oldrev` on code changes | Low |
| Force-push detection | No flag on `pull_request`; `push` event has `forced: true` | No flag; `oldrev` present on update, compare yourself | Medium |
| Webhook for comment / reply | `pull_request_review_comment`, `issue_comment`, `pull_request_review` | Note events (comments on commits/MRs/issues/snippets) | Low |
| Webhook for reactions on comments | **None — must poll Reactions API** | Emoji events (`award`/`revoke`), GA in 17.5 | **High** (GitHub gap) |
| Vercel-style check | Checks API: statuses, conclusions, markdown summary, annotations (50/request) — GitHub App only | Commit statuses API → `external` pipeline job in MR widget; no markdown tab, no annotations | **High** (GitLab gap) |
| Merge-blocking external check | Checks + branch protection | "External status checks" — **Ultimate tier only** | **High** |
| Inline diff comment | `line`/`side`/`start_line` + `commit_id` | Position object: `base_sha`/`head_sha`/`start_sha`, old/new path+line; brittle, known-bug warning | Medium |
| Batched review (N comments, 1 submit) | Create review with `comments[]` in one call | Draft notes + `bulk_publish` (multiple creates, one publish) | Low |
| Read reactions on own comments | Reactions API on issue comments & review comments (8 emojis) | Award-emoji API on notes | Low |
| OAuth sign-in for web UI | OAuth app or GitHub App user authorization (8 h token + 6 mo refresh) | OAuth app; full OIDC provider (`/.well-known/openid-configuration`) | Low |
| Self-managed / multi-instance | n/a (GHES out of scope) | Per-instance OAuth app registration; instance URL must be user-supplied | Medium |

## 1. App/auth model

**GitHub.** A GitHub App is the clear choice over OAuth apps/PATs: fine-grained permissions, install-time repo selection ("the user or organization owner who installed the app can decide what repositories the app can access"), a distinct bot identity, scaling rate limits, centralized webhooks, and — decisively — "Write permission for the REST API to interact with checks is only available to GitHub Apps" ([deciding-when-to-build-a-github-app](https://docs.github.com/en/apps/creating-github-apps/about-creating-github-apps/deciding-when-to-build-a-github-app), [checks/runs](https://docs.github.com/en/rest/checks/runs?apiVersion=2022-11-28)). "Add a repo via the web UI" maps to redirecting to the app's install page, where the user picks **All repositories** or **Only select repositories** ([installing-your-own-github-app](https://docs.github.com/en/apps/using-github-apps/installing-your-own-github-app)); the `installation` / `installation_repositories` webhooks tell us what we got ([webhook events](https://docs.github.com/en/webhooks/webhook-events-and-payloads)). Server-side auth: app JWT → `POST /app/installations/{id}/access_tokens`; the installation token "will expire after 1 hour" and can be down-scoped to specific repositories (max 500) and permissions ([generating-an-installation-access-token](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-an-installation-access-token-for-a-github-app)). PATs are per-user, manually managed, and unsuitable for a multi-tenant service ([managing PATs](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens)).

**GitLab.** No app/install primitive exists. Ingredients:
- **OAuth application** (user-, group-, or instance-owned; instance-wide apps are self-managed-admin-only) ([oauth_provider](https://docs.gitlab.com/integration/oauth_provider/)). Access tokens expire in **2 hours (7200 s)** with refresh tokens; refresh invalidates both old tokens ([api/oauth2](https://docs.gitlab.com/api/oauth2/)). Scopes are coarse relative to GitHub App permissions: `api`, `read_api`, `read_user`, `openid`, `profile`, `email`, `read_repository`, `write_repository` ([oauth_provider](https://docs.gitlab.com/integration/oauth_provider/)). Acting with a user's OAuth token means **the bot posts as that user** — no distinct identity/avatar.
- **Project access tokens** create a real bot user (`project_{id}_bot_{random}`) with its own identity, role + scopes, default 365-day expiry, and a rotate API — but on **GitLab.com they require Premium or Ultimate** (Free tier only on Self-Managed/Dedicated) ([project_access_tokens](https://docs.gitlab.com/user/project/settings/project_access_tokens/)). Group access tokens are analogous at group scope with the same GitLab.com paid-tier restriction ([group_access_tokens](https://docs.gitlab.com/user/group/settings/group_access_tokens/)).
- **Service accounts**: seatless machine users authenticating via personal access tokens; on GitLab.com only top-level group Owners can create them ([service_accounts](https://docs.gitlab.com/user/profile/service_accounts/)).

"Add a repo via the web UI" on GitLab therefore means: OAuth sign-in → list projects via API → use a token with Maintainer+ rights to `POST /projects/:id/hooks` with a secret `token` for payload validation ("You must be an administrator or have the Maintainer or Owner role for the project") ([project_webhooks API](https://docs.gitlab.com/api/project_webhooks/)).

## 2. Webhooks

**GitHub** ([webhook events and payloads](https://docs.github.com/en/webhooks/webhook-events-and-payloads)):
- PR opened / commits pushed: `pull_request` actions incl. `opened`, `reopened`, `ready_for_review`, `synchronize`. The `synchronize` payload carries `before`/`after` commit SHAs ([pull_request payload, actionType=synchronize](https://docs.github.com/en/webhooks/webhook-events-and-payloads?actionType=synchronize#pull_request)).
- Force-push: `pull_request` has **no forced flag**; the `push` event includes `before`, `after`, and `forced` (boolean). Detect via the `push` event on the source branch, or by noticing `before` is no longer an ancestor.
- Review comments: `pull_request_review_comment` (`created`/`edited`/`deleted` — "a comment on a pull request diff"), `pull_request_review` (`submitted`/`edited`/`dismissed`), `pull_request_review_thread` (`resolved`/`unresolved`). General PR conversation comments arrive as `issue_comment` ("a comment on an issue or pull request"). Replies to review comments are themselves `pull_request_review_comment` events.
- Reactions: **no webhook event exists for emoji reactions** — confirmed absent from the events list. Workaround: poll the Reactions API (below).

**GitLab** ([webhook events](https://docs.gitlab.com/user/project/integrations/webhook_events/)):
- MR events: actions `open`, `close`, `reopen`, `update`, `approval`/`approved`, `unapproval`/`unapproved`, `merge`. `object_attributes.oldrev` is "only available for the `update` action when there are actual code changes," e.g. new code pushed to the source branch — this is the new-commits/force-push signal (no explicit forced flag; compare `oldrev` vs new head yourself).
- Comment (note) events: fire when "a new comment is made or edited on commits, merge requests, issues, and code snippets"; `object_attributes.action` is `create`/`update`. Replies are notes within a discussion and arrive as note events (payload includes position data for diff notes).
- **Emoji events: yes.** "Introduced in GitLab 16.2 with a feature flag named `emoji_webhooks`... Enabled on GitLab.com in 16.3. Enabled by default in 16.4. Generally available in GitLab 17.5." Fires when a reaction is added/removed on issues, MRs, snippets, wiki pages, and **comments on those**, with `object_attributes.action` = `award` | `revoke`.
- Push events include `before`/`after` SHAs.
- Gotcha: `emoji_events` appears in the project-webhooks API docs only as a *test trigger* value; it is not (currently) listed among the documented `POST /projects/:id/hooks` boolean parameters — verify at implementation time or enable via UI ([project_webhooks API](https://docs.gitlab.com/api/project_webhooks/)).

## 3. Check surface ("Vercel deploy check")

**GitHub Checks API** ([checks/runs](https://docs.github.com/en/rest/checks/runs?apiVersion=2022-11-28)): GitHub App-only for writes. Statuses `queued`/`in_progress`/`completed` (plus `waiting`/`requested`/`pending`); conclusions `success`, `failure`, `neutral`, `cancelled`, `skipped`, `timed_out`, `action_required` (`stale` set by GitHub). `output` supports `title`, markdown `summary`, `text`, `images`, and inline `annotations`: "The Checks API limits the number of annotations to a maximum of 50 per API request" — send additional update requests to accumulate more. This is the exact Vercel-check experience: named check row on the PR with status icon, details tab with rendered markdown, annotations surfaced in the Files-changed diff. (Legacy alternative: the [commit statuses API](https://docs.github.com/en/rest/commits/statuses?apiVersion=2022-11-28) works without an App but has no markdown/annotations.)

**GitLab commit statuses** ([POST /projects/:id/statuses/:sha](https://docs.gitlab.com/api/commits/#set-the-pipeline-status-of-a-commit)): states `pending`, `running`, `success`, `failed`, `canceled`, `skipped`; params `name`/`context`, `target_url`, `description`, `ref`, `coverage`, `pipeline_id`. Statuses appear as jobs in an `external` stage: GitLab "searches for the most recent non-archived CI pipeline for the given commit SHA and ref" and appends, else "creates a new pipeline" with `CI_PIPELINE_SOURCE` = `external`; results show in MR and commit views ([external commit statuses](https://docs.gitlab.com/ci/ci_cd_for_external_repos/external_commit_statuses/)). **Cannot match GitHub:** no markdown summary tab (only a short `description` + `target_url` linking off-platform) and no inline annotations from the status.

**GitLab external status checks** ([status_checks](https://docs.gitlab.com/user/project/merge_requests/status_checks/)): **Tier: Ultimate** only. GitLab POSTs to the external service on MR update/close/reopen/approve/unapprove/merge; the service responds via the [status checks API](https://docs.gitlab.com/api/status_checks/) with `pending`/`passed`/`failed`; "Status checks must succeed" can block merge. Not viable as the baseline surface for a product targeting Free/Premium users — commit statuses are the portable answer.

## 4. Review comment APIs

**GitHub** ([pulls/comments](https://docs.github.com/en/rest/pulls/comments?apiVersion=2022-11-28), [pulls/reviews](https://docs.github.com/en/rest/pulls/reviews?apiVersion=2022-11-28)):
- Inline comment: `POST /repos/{owner}/{repo}/pulls/{n}/comments` with `commit_id`, `path`, `line` ("the line of the blob in the pull request diff... for a multi-line comment, the last line of the range"), `side` (`LEFT` deletions / `RIGHT` additions), optional `start_line`/`start_side`, `subject_type: file` for file-level.
- Replies: `POST .../comments/{comment_id}/replies` with just `body`.
- **Batched review:** `POST /pulls/{n}/reviews` accepts a `comments[]` array (each with `path`, `body`, `line`/`side`/`start_line`) plus `event` = `APPROVE` | `REQUEST_CHANGES` | `COMMENT` (omit for pending) — many inline comments in one call/notification.
- Reading reactions: [Reactions API](https://docs.github.com/en/rest/reactions/reactions?apiVersion=2022-11-28) lists reactions on issue comments and PR review comments; content values `+1`, `-1`, `laugh`, `confused`, `heart`, `hooray`, `rocket`, `eyes`. REST-only — poll to see thumbs on the bot's comments.

**GitLab** ([discussions API](https://docs.gitlab.com/api/discussions/#create-a-new-thread-in-the-merge-request-diff), [draft_notes](https://docs.gitlab.com/api/draft_notes/), [emoji reactions](https://docs.gitlab.com/api/emoji_reactions/)):
- Inline comment: `POST /projects/:id/merge_requests/:iid/discussions` with `position[base_sha]` (base of source branch), `position[head_sha]` (MR HEAD), `position[start_sha]` (commit in target branch), `position[position_type]=text`, `old_path`/`new_path`, and line rules: added line → `new_line` only; removed line → `old_line` only; unchanged line → **both**. Pitfall documented in-doc: "if you specify incorrect `base`/`head`/`start`/`SHA` parameters, you might run into" a known bug (issue #296829) — positions must match the current diff exactly, so stale lines after a new push are a real failure mode to handle (recompute against fresh `diff_refs`).
- Replies: `POST .../discussions/:discussion_id/notes`; resolve a thread with `PUT ... resolved=true`.
- **Batched review equivalent: yes — draft notes.** `POST .../draft_notes` (with optional `position` — "if omitted, creates a regular discussion note"), then `POST .../draft_notes/bulk_publish` "publishes all pending draft notes for a merge request that belong to the user," optionally with a summary note. Multiple create calls, single publish — semantically equivalent to a GitHub review submit.
- Reading reactions: award-emoji endpoints on notes, e.g. `GET /projects/:id/merge_requests/:iid/notes/:note_id/award_emoji` ("GitLab objects that accept emoji reactions are called awardables") — and unlike GitHub, emoji webhook events can push these to us. Non-diff MR comments use the [notes API](https://docs.gitlab.com/api/notes/).

## 5. OAuth sign-in for the web UI

- **GitHub:** classic [OAuth app web flow](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps), or reuse the GitHub App itself for user authorization ([generating a user access token](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app)); with expiration enabled "the user access token expires after eight hours, and the refresh token expires after six months" ([refreshing user access tokens](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/refreshing-user-access-tokens)). One app can serve both sign-in and installation.
- **GitLab:** OAuth with authorization code + PKCE ([api/oauth2](https://docs.gitlab.com/api/oauth2/)); GitLab is a full **OIDC provider** with `/.well-known/openid-configuration` discovery and standard `openid`/`profile`/`email` scopes, on GitLab.com and self-managed, all tiers ([openid_connect_provider](https://docs.gitlab.com/integration/openid_connect_provider/)). **Self-managed implication:** OAuth apps are registered per instance (user/group-owned, or admin-created instance-wide apps on self-managed) ([oauth_provider](https://docs.gitlab.com/integration/oauth_provider/)) — the product must accept an instance base URL and per-instance client ID/secret, likely entered by the customer's admin.

## Divergences that constrain design

1. **No install primitive on GitLab.** GitHub's "pick repositories, get webhooks + tokens automatically" collapses into three manual GitLab steps: OAuth grant, per-project webhook creation (Maintainer+ required), and separate credential provisioning. The "add a repo" UX and the data model (installation vs. per-project connection) must be abstracted.
2. **Bot identity is free on GitHub, paid/awkward on GitLab.** GitHub Apps always act as `app[bot]`. On GitLab.com a distinct identity needs a project/group access token (**Premium+**) or a group-owner-created service account; the fallback — user's OAuth token — posts reviews *as the user*.
3. **Check richness gap.** GitLab commit statuses give a named pass/fail job with `description` + `target_url` only; no markdown summary tab, no inline annotations from the check. Rich content must live in MR comments/discussions + an external details page. Merge-blocking external checks are **Ultimate-only**.
4. **Checks API is GitHub-App-gated** — locks the GitHub architecture to a GitHub App (fine, but it forecloses PAT/OAuth-app shortcuts).
5. **Reactions eventing is inverted.** GitLab pushes emoji `award`/`revoke` webhooks (GA 17.5; self-managed < 16.4 may need the flag enabled); GitHub has **no** reactions webhook — thumbs-up/down feedback on GitHub requires polling the Reactions API with rate-limit budgeting.
6. **Force-push signals differ.** GitHub: `pull_request synchronize` (`before`/`after`) + `push.forced`. GitLab: MR `update` with `oldrev`, no forced flag — ancestry check needed. Normalize into one internal "head moved (force?)" event.
7. **Inline position fragility on GitLab.** Three SHAs + old/new path/line with strict line-type rules and a documented failure mode for mismatched SHAs; GitHub needs only `commit_id` + `line`/`side`. The comment-placement layer needs a GitLab-specific position resolver and stale-position retry/fallback (degrade to non-positioned discussion note).
8. **Token lifecycle differs everywhere.** GitHub: mint 1 h installation tokens on demand from app credentials (nothing stored per customer beyond installation ID). GitLab: store per-connection secrets — OAuth refresh tokens (2 h access tokens, refresh rotates both) and/or long-lived access tokens with 365-day expiry needing rotation reminders/automation.
9. **Self-managed GitLab multiplies configuration.** Per-instance OAuth app registration, instance URLs, version skew (e.g. emoji webhooks pre-17.5), and admin-created instance-wide apps — the GitLab connector must be instance-aware from day one.
10. **Webhook API doc gap:** `emoji_events` is documented as a webhook *test* trigger but not as a documented create-hook parameter — confirm programmatic enablement during the GitLab spike.
